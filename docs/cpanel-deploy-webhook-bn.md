> লেখা হয়েছে 2026-10-18 রাতে (T-56)। সব "আজকের প্রমাণ" সেই সন্ধ্যায় নিজে
> চালানো কমান্ডের আউটপুট, অনুমান নয়। ফাইলে কোনো গোপন তথ্য (টোকেন/পাসওয়ার্ড)

## ১. এটা চালু করলে কী লাভ?

আপনি CMS-এ কিছু সেভ বা Publish করলে সাইট স্ট্যাটিক HTML — তাই সাইট নতুন করে
তৈরি (rebuild) হতে হয়। এখন যা হয়:

| | এখন (webhook ছাড়া) | চালু করার পরে |
|---|---|---|
| সাধারণ লেখা/সেটিংস সেভ | ≤৫ মিনিট পর ওয়াচারের ক্রন-চেক পরিবর্তন ধরে → ~৩–৪ মিনিট বিল্ড | সেভের কিছুক্ষণ পরেই (৫ মিনিটের debounce শেষে) নিজেই টিক ছুটে যায় |
| ব্রেকিং নিউজ | cron-এর পরবর্তী পর্ব পর্যন্ত অপেক্ষা | **একেবারে সাথে সাথে** টিক (debounce কেটে যায়) |
| cron কোনো কারণে মিস করলে | পরের cron-এ ধরা পড়ে | webhook-ই পড়ে থাকা কাজ ধরে ফেলে |

**আজকের প্রমাণ:** আজ আপনার দুটি লেখা (article 31, 32) এই webhook ছাড়াই
লাইভ পর্যন্ত পৌঁছেছে (দুটিই HTTP 200) — অর্থাৎ বর্তমান ব্যবস্থাও কাজ করছে;
webhook শুধু সময় কমায় ও নিশ্চয়তা দ্বিগুণ করে।

## ২. ওয়েবহুকটা কোথায় যাবে?

এই URL-এ: `https://shikkha24-publish-watcher.abdullahalmamunmay.workers.dev/run-tick`

কেন এটাই: ওয়াচারটার ভেতরেই rebuild পাঠানোর প্রমাণিত মেকানিজম (GitHub token,
digest-গেট) আছে। GitHub-এর dispatch API সরাসরি টার্গেট করা যায় না, কারণ আমাদের
CMS-এর ট্রিগার (`cms/src/lib/rebuild-trigger.ts`) GitHub-এর দাবি করা
`event_type`/`ref` ফিল্ড পাঠায় না।

**আজকের প্রমাণ (গুরুত্বপূর্ণ):** লাইভ ওয়াচারে `POST /run-tick` হেডার ছাড়াই
চালিয়ে দেখেছি — দুবারই `200 {"action":"unchanged"}` এসেছে। অর্থাৎ ডিপ্লয় করা
ওয়াচারে এই রুটটি এখনো **খোলা**; রেপোতে থাকা নিরাপদ সংস্করণটি (commit `bdccf53`,
টিক-সিক্রেট ছাড়া 404) এখনো ডিপ্লয় হয়নি।

## ৩. শুরুর আগে — ২টি কাজ (এগুলো আমি করব, আপনার শুধু অনুমোদন দিন)

1. **ওয়াচার হালনাগাদ:** রেপোর হার্ডেনড সংস্করণ (`bdccf53`) ডিপ্লয় + `TICK_SECRET`
   নামে একটি গোপন কী সেট। এতে `/run-tick` শুধু সেই গোপন কী জানা যে-কেউ টিক
   চালাতে পারবে না। টোকেন কখনো চ্যাটে পেস্ট করতে হবে না।
2. **CMS-এ ২ লাইনের পরিবর্তন:** `rebuild-trigger.ts` এখন শুধু `Authorization`
   হেডার পাঠায়; হার্ডেনড ওয়াচার `X-Tick-Secret` চায়। পরিবর্তনটি চলমান CMS
   ডিপ্লয় সাইকেলের (T-31 clean-cycle) সাথেই যাবে — আলাদা ডিপ্লয় লাগবে না।

এই দুটির পরেই নিচের "DEPLOY_WEBHOOK_TOKEN"-এর মান হবে সেই Tick-secret এর একটি
কপি। এগুলোর আগেও গাইড চালাতে পারেন — কিছু ভাঙবে না; ওয়াচার হার্ডেন হওয়ার পর
টোকেন যোগ না করা পর্যন্ত webhook নীরবে খারিজ হবে, আর সবসময়-পরিচিত ৫ মিনিটের
cron ব্যবস্থাটা পেছনে কাজ চালাতেই থাকবে।

## ৪. cPanel-এ আপনার ধাপগুলো

> লগইন: আপনার DianaHost cPanel (maddisonhost নয় — হোস্ট `b201.serverdiana.com`,
> ইউজার `shikkhac`)। অ্যাপের ডিরেক্টরি: `~/shikkha24-cms`।

### ধাপ ১ — ফাইল ভার্সনের ব্যাকআপ নিন (পথ B-এর জন্য দরকার, নিরাপত্তা সবার জন্য)

1. cPanel → **File Manager** → `home/shikkhac/shikkha24-cms`-এ যান।
2. ডান-উপরের **Settings** → **Show Hidden Files (dotfiles)** টিক দিন → Save।
3. `.env` ফাইলটিতে ডান ক্লিক → **Copy** → নাম দিন `.env-backup-আজকেরতারিখ`।

### ধাপ ২ — দুটি ভেরিয়েবল যোগ করুন

**পথ A (UI থেকে — আগে এটাই চেষ্টা করুন):**

1. cPanel → **Setup Node.js App** (বা Application Manager) → আপনার অ্যাপটি
   খুলুন (Application root: `shikkha24-cms`, Startup file: `cms/server.js`)।
2. **Environment variables** সেকশনে **Add Variable** দিন, দুইবার:

   | নাম | মান |
   |---|---|
   | `DEPLOY_WEBHOOK_URL` | `https://shikkha24-publish-watcher.abdullahalmamunmay.workers.dev/run-tick` |
   | `DEPLOY_WEBHOOK_TOKEN` | (৩ নম্বর কাজ শেষে আমি যে-গোপন কী দেব, তার কপি) |

3. **Save** চাপুন।

⚠️ **ইতিহাস:** 2026-10-15-এ এই UI-সেভ হোস্টের shell-সমস্যায় ("cagefs … Unable
to fork", টিকেট #0590191) কিছু ক্ষেত্রে আটকে গিয়েছিল। এরপর হোস্ট NPROC সীমা
বাড়িয়েছে, তাই এখন কাজ করতে পারে — আটকে গেলে অবাক হবেন না, পথ B ব্যবহার করুন।

**পথ B (ফাইল এডিট — নিশ্চিত রাস্তা):**

1. File Manager-এ `~/shikkha24-cms/.env` → ডান ক্লিক → **Edit**।
2. ফাইলের একদম নিচে এই দুই লাইন যোগ করুন (কোনো উদ্ধৃতিচিহ্ন নয়, অতিরিক্ত
   ফাঁকা স্পেস নয়, কোনো লাইনের আগে/পরে কিছু নয়):

   ```
   DEPLOY_WEBHOOK_URL=https://shikkha24-publish-watcher.abdullahalmamunmay.workers.dev/run-tick
   DEPLOY_WEBHOOK_TOKEN=<৩ নম্বর কাজ শেষে পাওয়া গোপন কী>
   ```

3. **Save Changes** → এডিটর বন্ধ করুন।

### ধাপ ৩ — অ্যাপ রিস্টার্ট করুন (এটা ছাড়া কিছুই কার্যকর হয় না)

- Setup Node.js App → অ্যাপটি খুলে **Restart** বোতাম; **অথবা**
- File Manager → `~/shikkha24-cms/tmp/restart.txt` ফাইলে ক্লিক করে **Edit** →
  কিছু না বদলে সেভ করুন (মোডিফিকেশন-টাইম বদলালেই Passenger নতুন করে চালু হয়)।

⚠️ **জরুরি টীকা:** আঘাতটা স্বাস্থ্যকর রাখতে রিস্টার্টের পরে পুরনো আটকে-থাকা
`next-server` প্রসেস আছে কি না দেখা ও মারা দরকার হয় (10-17-এ রিস্টার্টেও
জমে-থাকা প্রসেস পুরনো কোড সার্ভ করতে দেখা গিয়েছিল)। **এই অংশটা আপনার একা
করার দরকার নেই — বললেই আমি UAPI দিয়ে করে দেব এবং প্রমাণসহ জানাব।**

## ৫. এই কাজের পরিচিত ফাঁদগুলো

- `.env`-এ মানের দুপাশে উদ্ধৃতিচিহ্ন বা ফাঁকা স্পেস দিলে মান ভেঙে যায়।
- সেভ করে **রিস্টার্ট না করার** ফলে পুরনো প্রসেস পুরনো ভ্যারিয়েবলই দেখে।
- UI-সেভে "cagefs/fork" জাতীয় ত্রুটি হলে হোস্টে টিকেট লাগতে পারে — পথ B দিয়ে
  কাজ চলে যায়; আমাকে জানালে টিকেটের ভাষাটাও বানিয়ে দেব।
- `DEPLOY_WEBHOOK_TOKEN` গোপন কী — এমেইল/মেসেজে পাঠাবেন না, আমাকেও চ্যাটে
  পেস্ট করতে হবে না (আমি সবসময় secret সরাসরি হোস্টে বসাতে পারি)।
- ব্রেকিং নিউজের debounce কাটে যায় — অর্থাৎ ব্রেকিং খবরে সাইট সবচেয়ে দ্রুত
  নতুন হয়, সাধারণ লেখায় ৫ মিনিট পর্যন্ত সময় নেয় (নিচু লোড রাখার ইচ্ছাকৃত
  নকশা)।

## ৬. আজকের পরীক্ষার প্রমাণ (সন্ধ্যা ২২:০০–২২:৪৫ +06)

| পরীক্ষা | ফল |
|---|---|
| `POST /run-tick` (হেডার ছাড়া) ×২ | `200 {"action":"unchanged"}` — রুট এখন খোলা; রেপোর `bdccf53` এখনো ডিপ্লয় নেই |

গাইডটি বাস্তবায়নে কোনো ধাপে আটকে গেলে থামবেন না — যে ধাপে আটকেছেন তার নাম
বললেই আমি ওটা করে দেব বা পরের নিরাপদ বিকল্প দেখাব।
