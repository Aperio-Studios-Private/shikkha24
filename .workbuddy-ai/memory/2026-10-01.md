# Later still — "is there anything left?" → S9's last open build item (`f33bea8`, `6c11b01`)

## The audit first
Grepped `.sps/task.md` for every unchecked box and classified them. **All but one
were owner gates**: production-only measurements (Lighthouse, TTFB, device matrix),
DNS/SMTP/OAuth credentials, launch approvals. The one real build item was
**bookmark → CMS sync**, deferred since S9 (approved 2026-09-13) pending a product
decision.

⚠️ **That grep is the right first move when asked "is anything left?"** — the task
file is the record, and guessing from memory would have missed this.

## ⚠️ The deferred decision was already written down
`S9.md` said: "Correct behaviour needs the server to become authoritative after the
first upload... A naive union re-adds a bookmark that was deleted on another device
— the reader deletes something and it comes back, which is worse than never
syncing." So the policy was **recorded**, not guessed. The owner had already
delegated the call ("best practice").

**As built:** never-synced → merge (the local list is then *independent*, not
stale — that is what carries pre-login bookmarks); already-synced → server wins;
**a local change whose push failed outranks the server** (an intent it has not heard
yet; dropping it loses it silently).

## ⚠️ The marker had to go on the reader, not in local storage
`readers.bookmarksSyncedAt`. A per-device marker lets a device that **lost its
storage** re-upload a stale list and resurrect the deletion — the exact bug the
policy exists to prevent. It is also **not writable by the reader**: flipping it
back to "never synced" does the same thing deliberately.

## ⚠️ Two other decisions worth remembering
- **`bookmarks.title` / `bookmarks.slug` are a deliberate denormalisation.** A
  reader signing in on a second device has **no local list at all** — that is the
  point of syncing — so the server must return something renderable. Storing only
  the relationship id would force a resolve through the articles API before the
  list could be drawn.
- **The island is NOT in the layout.** Article page + `/bookmarks` only, and it
  makes no request unless the reader has synced before, has local bookmarks, or is
  on `/bookmarks`. A script on every page for a feature most readers never use is a
  cost paid by everyone for the few.

## ⚠️ Endpoint mounting — the trap again, avoided by reading the note
`/api/bookmarks/sync` at the API root would be parsed as "collection `bookmarks`,
document id `sync`" and 404 forever. **Collection endpoints are matched before the
generated routes**, so they are registered on the collection with relative paths.
This is the `/api/comments/submit` lesson (`docs/security.md` §13.4).

## Verification, and the one honest gap
- `verify:endpoints` → **7 new checks over HTTP** (49/49 total), including the two
  that matter: **an already-synced reader's stale upload is ignored**, and **a
  deleted bookmark does NOT come back on the next sync**.
- `verify:bookmarks` → **11 checks** on the pure merge policy
  (`frontend/src/lib/bookmark-merge.ts`), wired into `pnpm verify` and CI.
- ⚠️ **The island's own `fetch`/`localStorage` glue has NO behavioural test.** This
  project has no browser harness, so it is verified by construction plus the build
  and CSP gates. **Stated, not implied** — it is the weakest link in the feature.

## Refactor taken while here
`readerIdFromRequest` moved into `lib/reader-session.ts`. The parse-and-range-check
of the session id was about to exist in two endpoints, and it is the one place that
decides who a request is — two copies would be two chances to disagree. Reactions
now uses it; `verify:endpoints` confirms nothing moved.

# Pre-deployment secret-safety audit (`c656a25`)

Six-area audit before deploying. **The headline is that the repo was already in
good shape** — but three real findings, all fixed.

## What was wrong

1. ⚠️ **A hardcoded fallback signing key, twice.** `lib/reactions.ts` and
   `endpoints/poll-vote.ts` keyed their HMACs with `PAYLOAD_SECRET || <literal>`.
   Those hashes **are** the anti-stuffing controls (the reaction dedupe fingerprint
   and the poll duplicate-vote guard), so a published key lets anyone cast
   unlimited "unique" reactions or votes. `payload.config.ts` also refuses to boot
   without `PAYLOAD_SECRET`, so the fallback is unreachable **today** — but a
   predictable key is exactly what a later refactor revives by accident.
   → `requirePayloadSecret()` in `lib/signed-token.ts` **throws**; both call it.
2. ⚠️ **A superAdmin fixture with a hardcoded password.** `verify/reporter.ts`
   created three accounts, one a superAdmin, with literal passwords. The `finally`
   cleans up, but a **crash leaves a live admin account with a published
   credential**. → random per-run `randomBytes(24)`.
3. **Dead/mis-prefixed vars in the local `.env` files.** Six dead R2 variables (R2
   descoped 2026-09-14), a dead `NEXT_PUBLIC_SITE_URL`, two `PUBLIC_OAUTH_*` that
   contradicted the documented "credentials live in cms/.env only". None was read
   by any code — verified first. Backups written.

## What was checked and is clean — the more useful half

- **Git history: no `.env` was ever added**, and no commit holds a secret-shaped
  assignment. Only `.env.example` is tracked.
- **Nothing reaches the browser.** Every secret env *value* was searched for across
  **934 built files** — absent. No secret env *name* appears in built output.
  Astro exposes only `PUBLIC_*`; all 16 are public by design.
- **Logs/responses:** no `console.*` prints a secret; `rebuild-trigger` logs a
  status and a message, never the webhook URL or its bearer. `GET /api/oauth/me`
  returns id/name/avatar/provider only — never email or provider id.
- **Token gates fail closed:** unset `PUSH_SEND_TOKEN` / `NEWSLETTER_SEND_TOKEN`
  authorises **nobody**, both with `timingSafeEqual`.

## ⚠️ Technique worth reusing
Scanning for secrets by *value* is the only way to prove a build does not leak one:
read the env files, classify each value as public-or-not, then search every built
file for the sensitive ones. Grepping for env var *names* alone proves nothing —
Vite inlines the **values**.

## ⚠️ For the owner before going live
Rotate `PAYLOAD_SECRET`, and search any database a harness has run against for
leftover `verify-*@example.test` users. Rotating invalidates every outstanding
reader session — that is the intended effect, not a side effect.

## Also corrected
The README still said **"PRE-BUILD — nothing has been built yet"** on a fully built
project. Fixed, with a pointer to the new "Secrets — read this before deploying"
section.

# Personal-data flow audit (`cadfd2f`)

Seven-area audit of how reader data enters, travels and ends up. **The app was
already careful** — data minimisation is written into the collections, PII fields
are field-level restricted, and no log prints personal data. The real gap was a
promise the privacy policy could not keep.

## ⚠️ The finding: the policy promised deletion, and there was no way to do it
`privacy-policy.astro` said a reader could request deletion at any time — and the
only route was emailing the newsroom. On a site about scholarships and admissions,
the data in question is **what someone is applying for**. Now self-service:
`POST /api/readers/delete-account` + a control on `/bookmarks`.

⚠️ **Deletion vs anonymisation is the whole design**, and it is printed in the UI
rather than discovered afterwards:
- **Deleted:** the reader row, bookmarks, saved-deadlines, push-subscriptions,
  reader-linked reactions, and a matching newsletter-subscribers row.
- **Anonymised:** their **comments**. A published comment is part of the public
  record — the row survives, the byline becomes «একজন পাঠক», the email is cleared,
  the reader link is dropped.
- ⚠️ **Poll votes and anonymous reactions cannot be deleted, and that is not a
  gap.** They are keyed by a one-way HMAC of IP + UA with no reader link —
  deliberately, so they cannot be joined back to a person *even by us*. Nothing to
  erase because nothing identifies them.

⚠️ **`forgetBookmarkSync()` must clear the MARKER, not just the list.** Leaving the
marker behind makes a later account on the same browser look "already synced", and
its first sync then **discards** the local list instead of merging it.

## ✅ What was already clean — the more useful half
- **Passwords: readers have NONE** (`disableLocalStrategy`). Staff accounts use
  Payload's PBKDF2-HMAC-SHA256 — verified by reading
  `payload/dist/auth/strategies/local/generatePasswordSaltHash.js` **and** matching
  it against the stored hashes (32-byte salt, 512-byte output). A real KDF, **not**
  "SHA256 alone".
- **Logs:** no `console.*` in `cms/src` prints user data — only PASS/FAIL labels and
  counts. `rebuild-trigger` logs a status and a message, never the URL or its bearer.
- **PII fields are field-level restricted:** `Comments.userEmail`,
  `CitizenSubmissions.reporterEmail` / `.reporterPhone` are `read: Boolean(req.user)`,
  so an anonymous read cannot enumerate them even if a collection rule loosens.
- **No raw IP is stored anywhere.** Reactions and poll votes keep only a one-way
  HMAC; rate limits live in memory.
- **Cookies:** reader session and OAuth state are `HttpOnly; SameSite=Lax; Secure`
  in production.
- **No PII in localStorage.** What is there is preferences and interests (theme,
  text scale, bookmarks, reactions, quiz streak, district/coords) — never a name,
  email, phone or token.
- **CSRF** is enforced (`csrf: ALLOWED_ORIGINS`), so a cross-origin cookie POST is
  rejected.

## ⚠️ Two findings RECORDED but not fixed — owner decisions
1. **PBKDF2 at 25,000 iterations** is below current OWASP guidance for
   PBKDF2-SHA256. It is Payload's default with **no config knob** — changing it
   means patching the framework. Exposure is a handful of staff accounts.
2. **Social login requests the `email` scope and nothing reads it.** The Readers
   collection itself says nothing logs in by email. Dropping it is one line and
   shrinks the consent screen, but it is user-visible.

## ⚠️ Technique worth reusing
Audit data flows by **collection point → storage → external destination**, and
check *response shape* as well as *access rules*. Every public endpoint here returns
`{ ok: true }` or a deliberately narrow object; `GET /api/oauth/me` returns
id/name/avatar/provider and never the email or provider id. An access rule that is
correct can still be undone by a response that echoes too much.

## ⚠️ Check 4 — Security headers on the CMS  FIXED
The static frontend already had HSTS, nosniff, X-Frame-Options DENY, CSP etc via

## ⚠️ Check 5 — Per-IP rate limiting on auth endpoints  FIXED
Payload's `maxLoginAttempts: 5` is per-account; an attacker can try 5 passwords
against every account. Added:
- `/api/users/login` → 5/min per IP
- `/api/users/forgot-password` → 3/hour per IP

catch-all `[...slug]`. They check the limit, return 429 with `Retry-After`, and
delegate to `REST_POST(config)`.

**Why this shape:** Next 16 deprecated middleware; Payload's `beforeLogin` hook
runs AFTER the password check; auth operations do not run collection hooks.
A specific route handler is the only intercept point that exists.

  degrade gracefully (unset token = nobody authorised).
- **Check 2 (debug code):** no TODO/FIXME/XXX/HACK referencing security; no test
  endpoints; no `console.log` debugging.
- **Check 3 (error handling):** no stack trace, SQL, file path or internal detail
  leaks. Every client error is a generic message.
- **Check 6 (CORS):** explicit allow-list, not wildcard. Production trusts only

- **Check 7 (database):** SQLite file-based, no network port, no default creds,

# Deep security audit — critical paths (`5dd924a`)

## Scope note
The request included payment logic (Stripe, Razorpay), but this app is an
education news portal with **no payments at all** — no paid features, no payment
providers. The audit covered what actually exists: authentication (staff local
auth + reader OAuth), authorization, and input handling.

## Findings

### FIXED — Path traversal in `mediaFilePath` (`cms/src/lib/id-card.ts`)
The function used `path.resolve()` without verifying the result stayed inside
the media directory. While Payload's upload pipeline sanitises filenames via
`sanitize-filename`, a second line of defence is warranted: a bypass in the
upload layer (CVE, compromised admin, database tampering) would allow arbitrary
file read. Added `resolved.startsWith(base + path.sep)`. Verified against 6
attack variants (`../../../etc/passwd`, `/etc/passwd`, nested traversal, etc.).

### FIXED — Duplicate `clientIp` in `poll-vote.ts`
The endpoint defined its own `clientIp()` identical to the shared helper. Future
edits to one could diverge. Removed the local copy; now imports from `lib/http.ts`.

### DOCUMENTED — Password reset token not explicitly cleared (INFO)
After reset, Payload sets `resetPasswordExpiration` to the current date,
invalidating the token. The token string remains in the DB column. Not
exploitable today, but a latent risk if a backup is restored or the expiration
check regresses. Fix documented: an `afterChange` hook that clears the token
when expiration is set to a past date.

### DOCUMENTED — Stateless reader sessions cannot be revoked server-side (INFO)
Logout clears the cookie, but a stolen copy remains valid for 30 days. This is
the standard stateless-session trade-off, mitigated by `HttpOnly; Secure;
SameSite=Lax`. Adding revocability would require a session-generation counter on
the reader row; documented as a cost-benefit decision.

## Verified clean
- **No IDOR:** every endpoint derives identity from the session cookie, never
  from the body. `readerIdFromRequest()` is the single source of truth.
- **No SQL injection:** zero raw SQL; all queries through Payload's ORM.
- **No XSS:** `lexicalToHtml` escapes every text node (`& < > " '`); `safeUrl`
  rejects `javascript:` and `data:` schemes; comments use Astro's default
  escaping; no `set:html` on user input.
- **No mass assignment:** every write endpoint builds data key-by-key; no body
  spread anywhere.
- **No open redirect:** OAuth `next` is inside signed state, validated by
  `safeNextPath()` which rejects anything not site-relative.
- **Strong password hashing:** PBKDF2-HMAC-SHA256, 25,000 iterations, 32-byte
  salt, 512-byte output.
- **Proper file upload validation:** MIME whitelist, 15 MB cap, WebP conversion,
  dimension capping (2000px), EXIF/metadata stripping, per-day quota,
  `sanitize-filename`.
- **Token security:** 160-bit entropy (`crypto.randomBytes(20)`), 1-hour expiry,
  single-use via expiration, timing-safe comparison, context binding.
