# S15 — Live TV (built and verified)

## What shipped
`LiveStreams` collection · `MediaEmbed.astro` (ONE click-to-load player for **both**
YouTube and Facebook — the owner chose both, and they differ only in the frame URL, so
the behaviour, the reserved 16:9 box and the runtime re-validation exist once) ·
`/live-tv` · a footer link · a sitemap entry · a `liveTvTop` ad position.

## The architectural change: a THIRD CSP profile
`/live-tv` frames YouTube **and** Facebook. Strict is `frame-src 'none'`; the relaxed
profile carries **no video at all** — so tagging the route `RELAXED` blocks the player
**silently**. Widening `RELAXED` was rejected as a security regression (the homepage,
every category listing and `/quiz` would gain iframe permission they do not need).

**`SHIKKHA24_CSP_MEDIA`, scoped to `/live-tv` alone.** ⚠️ Three things fail silently on
their own, so all three are asserted: a tagged route with no consuming `Header` falls to
**strict**; the tag leaking sitewide; and `frame-src` omitting one provider. The relaxed
profile is now asserted to carry **no** video host, so the rejected option cannot be
quietly reintroduced.

⚠️ **`verify-apache.mjs` keys the expected profile on `data-media-embed`** — the
attribute the player component emits — not on the `/live-tv` path. A path key would be a
second copy of the `.htaccess` regex (the M14/M16 mistake). The route loop was
restructured at the same time: its old `hasAd`-first branching mis-classified a media
page with no ad slot as merely "over-relaxed". New logic keys on the **direction that
matters** — needing a relaxation and not getting it is a failure; having a wider policy
than needed is a note.

**Counter-proved:** the tag was stripped from both `.htaccess` copies → `verify:apache`
reported `/live-tv … got strict`, `verify:build-output` reported
`0 rule(s) matching /live-tv`. Both red. Restored, re-verified in sync.

## Traps hit
1. ⚠️ **Payload's boolean field type is `checkbox`, not `boolean`.** `type: 'boolean'`
   fails `tsc` with `Type '"boolean"' is not assignable to …`. The error names the field,
   not the fix.
2. ⚠️ **A seeder's early-return path is a silent trap.** `seedDemoEngagement` bails out
   once the gallery exists — and that gallery predates S15, so on any existing database
   the early return is the **only** path taken. The first version of the live-stream
   fixture therefore created **nothing**, and the only signal was the seed report printing
   `liveTv 0`. **When adding a fixture to an idempotent seeder, check every return path.**
3. ⚠️ **The Drizzle stale-index trap fired on the new collection**
   (`payload_locked_documents_rels_order_idx already exists`) — exactly as recorded. A
   plain retry after the failed push succeeded; no manual `DROP INDEX` needed this time.
   **The database was backed up to `/tmp/payload-backup-*.db` first.**

# S16 — Reader Reactions (built and verified)

## What shipped
`Reactions` collection · `POST /api/reactions/toggle` + `GET /api/reactions/counts` (both
**collection-mounted**) · `ReactionBar.astro` island · `verify:reactions` (9/9) · a
privacy-policy disclosure · CI wiring.

## Decisions worth keeping
- ⚠️ **`Reactions.read` is NOT public — that is a privacy control.** A row holds a
  `fingerprint`, so a public read would let anyone enumerate every fingerprint on an
  article. The aggregate is computed server-side by the counts endpoint; only five counts
  plus the caller's own choice leave the CMS.
- ⚠️ **Two compound unique indexes, and both are needed.** `(article, type, reader)` for a
  signed-in reader (the account survives a cookie wipe); `(article, type, fingerprint)` for
  an anonymous one. **SQLite treats `NULL` as distinct in a unique index**, so the reader
  index cannot constrain an anonymous row at all.
- ⚠️ **The insert is deliberately not atomic** — two concurrent toggles can both see "no
  existing row". The unique index refusing the second is the control, so the handler catches
  that refusal and returns fresh counts rather than a 500.
- ⚠️ **Single-choice is an endpoint rule, not a DB rule.** The spec's two indexes do not make
  "one row per article per fingerprint" impossible, so a crafted request could record two
  different types. Recorded rather than silently adding two more indexes (rule 13).

## 🚨 The counter-proof needed a different method — the finding to keep
**Dropping the unique index out-of-band with `sqlite3` proves nothing.**
`payload run` **re-applies the declared schema on boot**, so the index was silently recreated
before the harness executed — and the harness **PASSED with the index "dropped"**. A
counter-proof that proved nothing, and it looked completely convincing.

The honest method: remove the index from the **collection config**; the schema push then drops
it for real, and the harness reports
`FAIL … a second row was created — the unique index is missing`. Restored byte-identical.

**Counter-prove a schema constraint via the config, never via the database.**

## Traps hit
1. ⚠️ **`pagination: false` is required on the counts query.** Payload's `find` returns one page
   by default, so counting `docs.length` without it silently caps the tally at the page size —
   a wrong number that looks like a real one (trap 10A).
2. ⚠️ **Payload *throws* `Forbidden`** when access is denied on `find`, rather than returning an
   empty page. A harness asserting only `docs.length === 0` fails on the throw.
3. ⚠️ **A relationship column needs a numeric id.** The reader session carries the id as a
   **string** (it is signed, not typed); `payload.create` rejects it for a numeric relationship.
   Parse and range-check rather than cast.
4. ⚠️ **The vocabulary lives in three places** — `cms/src/lib/reactions.ts`,
   `cms/src/collections/Reactions.ts` (admin labels), `frontend/src/lib/reactions.ts`. The CMS
   cannot be imported from the frontend (`node:crypto` + Payload). **Grepping for `angry` finds
   all three.**

· build-output (incl. "no baked counts") · links · apache · sync · `verify:reactions` 9/9 ·

# S17 — Photo Story & Video News (built and verified)

## What shipped
`Articles.layout` / `photoStory` / `videoUrl` / `videoProvider` · `PhotoStory.astro` +
`lib/photo-story.ts` · `lib/video.ts` · `MediaEmbed` above the body · `/video` hub ·
`ImageGallery` JSON-LD · `/video` tagged with the media profile · footer + sitemap entries.

## 🚨 The defect — the most valuable thing this section produced
**`Articles.videoProvider` can be `facebook`, but the article profile's `frame-src` named only
YouTube.** An article carrying a Facebook video would have been **silently dead on the
highest-traffic route**: HTTP 200, valid markup, a valid policy, and the iframe blocked with no
error anywhere.

It surfaced only because S17 made an *article* render a `MediaEmbed` for the first time, so
`verify:apache`'s expectation finally mismatched. Nothing else could have found it.

**Fix — two parts, and the second is the one that matters:**
1. The article profile gained the Facebook hosts in `frame-src`.
2. **The harness became provider-aware.** It reads `data-media-provider` off each page — the
   component's own statement of which provider the reader will frame — and asserts the served
   policy allows **that** provider. A blanket "does the policy mention Facebook" would not have
   caught it, because the real question is whether the policy permits the frame the page creates.

## ⚠️ Consequence: the article and media profiles are now byte-identical
Both env vars remain (they dispatch by different route families, so a later change to one cannot
silently widen the other), but **neither harness alone proves the dispatch any more** — the static
half is `verify:build-output`, the runtime half is `verify:apache`.

`profileOf()` now classifies by **capability** (`relaxed-video` / `relaxed-generic` / `strict`),
not by which env var produced the header. `expectedProfile()` returns `relaxed-video` when the page
renders `data-media-embed` **or** is a `NewsArticle` — the second because an article can embed a
video through its *body* block without ever rendering the component.

## Other traps
- ⚠️ **`/video/page/:n` needed its own rule.** It is 3 segments, and the article rule excludes only
  a `page/` in the **middle** position — so page 2 of the hub would have been served strict and its
  player would have died silently.
- ⚠️ **`/video` features the newest video with a player**, not just cards. The spec calls it a
  listing *and* decides it needs the media profile because it embeds; those only agree if it
  actually embeds. A page of plain cards needs no `frame-src` at all.
- ⚠️ **Fixtures must cover both providers.** With only a YouTube fixture the provider-aware check
  can never fire and the Facebook half of `MediaEmbed` never renders — **which is exactly how the
  defect survived.** One video article per provider is now seeded.

## Photo story notes
A layout, not a collection. Frames render **ahead of** the prose, never instead of it. Box
reservation measured at `--frame-ratio: 1600 / 1067` on all four frames; an unmeasurable image is
**skipped, not guessed**. Scroll-linked with pure CSS behind `@supports` +
`prefers-reduced-motion`, so the frames are readable with JavaScript off.

⚠️ The frame resolution lives in `lib/photo-story.ts`, not in the component, because the page needs
the same list **twice** — to render and to build the JSON-LD. Resolving independently in each place
is how structured data ends up describing images the page does not show.

## Counter-proofs
Stripping the `/video` tag → `/video → strict, but the page needs relaxed-video` (apache) and
`.htaccess tags /video` (build-output). Stripping the article profile's Facebook hosts →
`frames a Facebook video, but the policy forbids the frame` (apache) and
`the article profile frames Facebook` (build-output). Both restored and re-verified in sync.
