# 2026-09-30 — CMS access-control audit, and all eleven fixes

## What happened
The owner asked for an in-depth audit of whether the CMS is functioning 100% correctly, then for a
complete TODO list of every issue and a fix-one-at-a-time pass with verification after each.

**The CMS was not correct.** Six authorisation holes, four of them critical, all reachable by an
anonymous stranger — with **every existing gate green**.

## 🚨 The systemic finding
`403` and `Forbidden` appeared **zero times** across `cms/src/verify/*.ts`. The suite tested the
custom endpoints thoroughly and never once asserted that a *generated* REST route refuses the wrong
caller. That is why six holes shipped unnoticed. The fix for this is the most valuable artefact of
the session: `verify:access`.

## The holes, each proven with a real request before being fixed
| # | Collection | Defect | Proof |
|---|---|---|---|
| C1 | `media` | only `read` defined → create/update/delete fell to Payload's `Boolean(user)` default | `DELETE /api/media/999999` → **404 not 403**; any account could wipe the image library |
| C2 | `users` | `isSelfOrAdmin` compared a DOCUMENT id to the USER id; `users` and `readers` both number from 1 | `GET /api/users/1` with a reader session → **200** returning nameBn, `roles:["superAdmin"]`, phone. `PATCH … {email}` → 400 naming the email field = **writable** → password-reset takeover |
| C3 | `newsletter-subscribers` | `create: () => true`, and its justification ("so the endpoint's local-API call can write") was **false** — the endpoint uses `overrideAccess` | `POST` with `isActive:true` → **201, is_active=1**: double opt-in bypassed |
| C4 | `readers` | `create: () => true` | 201, then five more in **222 ms** — the entry point for C1/C2 |
| H1 | `bookmarks`, `saved-deadlines`, `push-subscriptions` | `isSelfOrAdmin` filtered on `id`, but ownership is the `reader` **relation** | reader saw a foreign row and not their own |
| M | `comments` | `create: () => true` bypassed the submit endpoint's rate limit and honeypot | 400 (validation) instead of 403 |

## ⚠️ The trap that cost the most time
**Payload's default access for an undefined rule is `Boolean(user)`** — "any authenticated account"
— not "anyone". Verified in `payload@3.89.0/dist/auth/defaultAccess.js`. So a collection that
defines only `read` is not read-only; it is **write-open to every logged-in account**.

## ⚠️ The second trap: Next.js does not reload the Payload config
A collection edit needs a **CMS restart** to take effect. The first T5 verification "failed" purely
because the dev server was still running the old config. Every verification after that restarted
the server first.

## The eleven tasks — all complete and verified
T1 media access · T2 `isSelfIn(collection)` + `email` field access · T3 newsletter create + `isActive`
· T4 readers create · T5 relation-based ownership helper · T6 comments create · T7 **`verify:access`**
· T8 `requireEnv` for `PAYLOAD_SECRET`/`DATABASE_URI` · T9 CORS localhost out of production · T10 env
template + stale collection count · T11 `authors.bloodGroup` hidden.

`isSelfOrAdmin` is now `isSelfIn('users' | 'readers')`, so the mistake is **unrepresentable** — the
caller must name the collection whose ids it compares. That was the root cause of three separate
defects (`authors` 2026-09-18, `users` and the relation-owned three on 2026-09-30).

## Verification method worth reusing
1. **Prove the hole first** with a real HTTP request, so the fix has something to be measured against.
2. **Fix, restart the CMS, re-run the same request** — the exact request that previously succeeded.
3. **Prove the feature still works** — closing `create` must not break the endpoint that legitimately
   writes (`/api/newsletter/subscribe`, the OAuth callback, `/api/comments/submit`).
4. **Prove no regression for the legitimate actor** — a real staff login still reads and writes its
   own record; an editorial session still reads `bloodGroup`; the press card still renders.
5. **Counter-prove the harness** — reintroduce each defect and confirm it goes red naming the right
   assertion.
6. **Restore the database and verify the counts.**

⚠️ **A counter-proof that "passes" on a crash is not a counter-proof.** The first attempt at the
bookmarks mutation referenced an unimported helper, so the harness *crashed* — non-zero exit, zero
FAIL lines. The counter-proof now treats "non-zero with no named assertion" as a failure.

## ⚠️ Caught while proving, not while assuming
Adding `verify:endpoints` to the CI local-API loop would have **turned CI red**: that loop boots
Payload in-process with no HTTP listener, and the harness makes real requests (`ECONNREFUSED`). It
was already correctly placed in the with-CMS step. Both steps were then verified locally in their
exact conditions: the 12-harness loop with **no server** → 0 failures; `with-cms.sh` running
sync + endpoints → exit 0.

## Also fixed: the gate table documented gates that did not exist
`docs/testing-and-qa.md` listed `verify:endpoints`, `verify:social` and `verify:rebuild-notice` as
"Every CI run" while **none** ran anywhere in the workflow. All three run now and the table matches.

## Final state
Root `pnpm verify` exit **0**, 0 FAIL lines · 12 harnesses in the CI loop pass with no server ·
`with-cms` step (sync + endpoints) exit 0 · 27-check HTTP access matrix ALL PASS · database restored
to its exact pre-audit counts (readers 0, subscribers 0, users 1, articles 24, comments 3) · repo
clean · 8 commits (`990ab97` … `58724b9`).

⚠️ **Not covered by this audit:** the admin UI itself (Payload admin views hydrate client-side — the

# T12 — the 3 high-severity dependency advisories, fixed and CI green

`pnpm audit --audit-level=high` began failing on a lockfile that had **passed two days earlier** —
new advisories, not a change here. Two transitive deps, both via Payload:
`undici` (TLS validation bypass in BalancedPool; WebSocket-subprotocol DoS) and `nodemailer`
(addressparser ReDoS).

⚠️ **Upstream has not fixed either.** Verified: the latest `payload@3.90.2` still pins
`undici: 7.29.0`, and the latest `@payloadcms/email-nodemailer@3.90.2` still declares
`nodemailer: ^9.1.1`. An override is the only fix.

## ⚠️ Override scoping matters more than the override
`undici` exists **twice** in this tree: `7.29.0` via Payload (vulnerable) and `8.10.2` via Astro's
`unifont` (not vulnerable). A bare `undici: 7.29.1` would have dragged **Astro's copy backwards a
major version**. The override key is `'undici@7.29.0'` — the exact vulnerable version — so it
targets only the instance that needs it and stops applying by itself when upstream moves.
Overrides live in `pnpm-workspace.yaml` (pnpm 10+; **not** `package.json`).

Result: **20 vulns (5 low / 12 moderate / 3 high) → 7 (2 low / 5 moderate / 0 high)**.
`pnpm audit --audit-level=high` exits 0.

## ⚠️ Two things I got wrong, both caught by checking rather than assuming
1. **A web search claimed nodemailer 10 relicensed to EUPL-1.1.** False — npm *and* the published
   tarball both report **MIT-0** for 9.1.1 and 10.0.6. That claim would have blocked a correct fix.
2. **nodemailer 10 IS a real break, just not a runtime one.** Its v10.0.0 notes list exactly one
   breaking change ("Node.js 20 or newer"), so I called it safe — and CI's CMS typecheck failed:
   `'auth' does not exist in type 'SMTPConnectionOptions'`. v10 moved `auth` from the *connection*
   options to `SMTPTransport.Options`, and Payload types `transportOptions` as the former. Fixed by
   building the options object as a **value** rather than an inline literal (the excess-property
   check only applies to fresh literals). Payload passes `transportOptions` straight to
   `createTransport`, which has always accepted `auth` — an upstream type narrower than the function.

## ⚠️ The sandbox cannot install — Trap 9
`pnpm install` dies with `CODEBUDDY_BROKER_DENY EEXIST` on the store's project symlink, or **hangs
indefinitely** (10 min observed). `--lockfile-only` hits it too. **The working sequence is: `rm -f`
the stale symlink and run the install in the SAME command**, so the single `registerProject` call
creates it fresh. Never run two pnpm invocations at once. `node_modules` still holds the old
versions locally; CI installs from the lockfile, so **CI is where the new versions are exercised**.

## Verification without an install
Since the sandbox blocks installing nodemailer 10, the published tarball was downloaded and
inspected directly: dual ESM/CJS `exports`, `createTransport` present on both. A focused type test
with the project's own `tsc` then proved the new shape passes against v10's real types — with a
`@ts-expect-error` guard on the old inline form, so the test is **not vacuous**.

⚠️ **It extends S10's N4, it is not a new feature.** `/institutions` + `/institutions/[slug]` already

## Agreed decisions (from the interview)
1. **Two axes** — keep `type` (public/private/NU-college/Islamic) and add `discipline`
   (general/engineering/medical/agricultural). BUET then appears under **both** Public and

2. **Auto news linkage** — a `university` relationship on `Articles`; the profile lists articles

3. **Hybrid fields + a visible "last verified" date.** A wrong fee is not a cosmetic error.

## ⚠️ The data survey — measured, and it changes the requested scope
Owner chose "full listing including all NU colleges". Four sources fetched and inspected:

| Source | Records | Bengali names | Licence |
|---|---|---|---|
| **Wikidata** (SPARQL) | 272 universities, 1,283 higher-ed | ✅ **271/272** universities; 880 higher-ed | **CC0** |
| GitHub `bangladesh-education-datasets` | 216 universities | ❌ English only | CC BY-SA 4.0 (Wikipedia-derived) |

⚠️ **The binding constraint: the site is BENGALI-ONLY and the NU college list is ENGLISH-ONLY.**
`/college-list` gives 2,274 uppercase English names, **no district field** (the portal filters

⚠️ **A query of mine returned "0 Bengali labels" and was WRONG** — a bug in how I read the label
service. The direct aggregate says **271 of 272**. Checking the aggregate instead of trusting my own

# S18 — the university directory model, built (commit `519c5b4`)

Picked up the one approved-but-unstarted section. Extends S10's N4 starter set per
`docs/university-directory.md` §2. **No access rule changed.**

## 🚨 The previous "hung Payload schema push" was a MISDIAGNOSIS
The most valuable finding of the day. The push was never the problem.
**`pnpm run` triggers pnpm 11's pre-run dependency check**, which shells out to `pnpm install` — and
in this sandbox that either dies with `CODEBUDDY_BROKER_DENY EEXIST` or **hangs indefinitely**
(10 min observed, twice). The earlier session read that hang as a drizzle failure and reverted six
working files.

**Fix:** run the tool directly — `cms/node_modules/.bin/payload run <script>` — or use a `pnpm` shim
that injects `--config.verify-deps-before-run=false`. The push then completes in seconds, and
`pnpm run`, the nested pnpm calls inside the project's own scripts, and `with-cms.sh` all work.

**The drizzle stale-index trap is real but separate**, and its trigger is narrower than recorded: it
bites a **pre-existing** DB whose schema predates the change (the push re-emits `CREATE INDEX` for
indexes that already exist, converging only over repeated attempts — drop the named index, retry).
**A fresh DB pushes cleanly AND is idempotent** — verified by booting one twice, so CI (fresh
`ci.db`) was never at risk.

## Two implementation decisions, both against the obvious choice
1. **`wikidataId` is indexed but NOT `unique`.** Payload does not coerce `''` → `null` for a text
   field (read in `payload/dist/fields/hooks/beforeValidate/promise.js`), so a unique index would
   reject the **second** institution saved by hand with a blank ID — and S21 authors ten by hand.
   Proven: two blank-ID rows both save. De-duplication belongs to the S19 import.
2. **`address` was preserved, not dropped.** The move into `contact` was applied as a real
   `ALTER TABLE … RENAME COLUMN` before the push, so all five seeded addresses survived.
