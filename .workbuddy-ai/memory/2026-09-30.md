# 2026-09-30 — CMS access-control audit, and all eleven fixes

## What happened
The owner asked for an in-depth audit of whether the CMS is functioning 100% correctly, then for a
complete TODO list of every issue and a fix-one-at-a-time pass with verification after each.

**The CMS was not correct.** Six authorisation holes, four of them critical, all reachable by an
anonymous stranger — with **every existing gate green**.

## 🚨 The systemic finding
`403` and `Forbidden` appeared **zero times** across `cms/src/verify/*.ts`. The suite tested the
custom endpoints thoroughly and never once asserted that a *generated* REST route refuses the wrong
caller. That is why six holes shipped unnoticed. The fix for this is the most valuable artefact of
the session: `verify:access`.

## The holes, each proven with a real request before being fixed
| # | Collection | Defect | Proof |
|---|---|---|---|
| C1 | `media` | only `read` defined → create/update/delete fell to Payload's `Boolean(user)` default | `DELETE /api/media/999999` → **404 not 403**; any account could wipe the image library |
| C2 | `users` | `isSelfOrAdmin` compared a DOCUMENT id to the USER id; `users` and `readers` both number from 1 | `GET /api/users/1` with a reader session → **200** returning nameBn, `roles:["superAdmin"]`, phone. `PATCH … {email}` → 400 naming the email field = **writable** → password-reset takeover |
| C3 | `newsletter-subscribers` | `create: () => true`, and its justification ("so the endpoint's local-API call can write") was **false** — the endpoint uses `overrideAccess` | `POST` with `isActive:true` → **201, is_active=1**: double opt-in bypassed |
| C4 | `readers` | `create: () => true` | 201, then five more in **222 ms** — the entry point for C1/C2 |
| H1 | `bookmarks`, `saved-deadlines`, `push-subscriptions` | `isSelfOrAdmin` filtered on `id`, but ownership is the `reader` **relation** | reader saw a foreign row and not their own |
| M | `comments` | `create: () => true` bypassed the submit endpoint's rate limit and honeypot | 400 (validation) instead of 403 |

## ⚠️ The trap that cost the most time
**Payload's default access for an undefined rule is `Boolean(user)`** — "any authenticated account"
— not "anyone". Verified in `payload@3.89.0/dist/auth/defaultAccess.js`. So a collection that
defines only `read` is not read-only; it is **write-open to every logged-in account**.

## ⚠️ The second trap: Next.js does not reload the Payload config
A collection edit needs a **CMS restart** to take effect. The first T5 verification "failed" purely
because the dev server was still running the old config. Every verification after that restarted
the server first.

## The eleven tasks — all complete and verified
T1 media access · T2 `isSelfIn(collection)` + `email` field access · T3 newsletter create + `isActive`
· T4 readers create · T5 relation-based ownership helper · T6 comments create · T7 **`verify:access`**
· T8 `requireEnv` for `PAYLOAD_SECRET`/`DATABASE_URI` · T9 CORS localhost out of production · T10 env
template + stale collection count · T11 `authors.bloodGroup` hidden.

`isSelfOrAdmin` is now `isSelfIn('users' | 'readers')`, so the mistake is **unrepresentable** — the
caller must name the collection whose ids it compares. That was the root cause of three separate
defects (`authors` 2026-09-18, `users` and the relation-owned three on 2026-09-30).

## Verification method worth reusing
1. **Prove the hole first** with a real HTTP request, so the fix has something to be measured against.
2. **Fix, restart the CMS, re-run the same request** — the exact request that previously succeeded.
3. **Prove the feature still works** — closing `create` must not break the endpoint that legitimately
   writes (`/api/newsletter/subscribe`, the OAuth callback, `/api/comments/submit`).
4. **Prove no regression for the legitimate actor** — a real staff login still reads and writes its
   own record; an editorial session still reads `bloodGroup`; the press card still renders.
5. **Counter-prove the harness** — reintroduce each defect and confirm it goes red naming the right
   assertion.
6. **Restore the database and verify the counts.**

⚠️ **A counter-proof that "passes" on a crash is not a counter-proof.** The first attempt at the
bookmarks mutation referenced an unimported helper, so the harness *crashed* — non-zero exit, zero
FAIL lines. The counter-proof now treats "non-zero with no named assertion" as a failure.

## ⚠️ Caught while proving, not while assuming
Adding `verify:endpoints` to the CI local-API loop would have **turned CI red**: that loop boots
Payload in-process with no HTTP listener, and the harness makes real requests (`ECONNREFUSED`). It
was already correctly placed in the with-CMS step. Both steps were then verified locally in their
exact conditions: the 12-harness loop with **no server** → 0 failures; `with-cms.sh` running
sync + endpoints → exit 0.

## Also fixed: the gate table documented gates that did not exist
`docs/testing-and-qa.md` listed `verify:endpoints`, `verify:social` and `verify:rebuild-notice` as
"Every CI run" while **none** ran anywhere in the workflow. All three run now and the table matches.
