## Demo-purge tooling (audit §2.8)

**The documented removal path did not exist.** `cms/src/seed/demo.ts` told the reader to run
`payload run src/seed/demo-purge.ts` — and no such file had ever been written. "Delete before
launch" therefore meant hand-deleting ~130 records across 22 collections in the admin UI.

**Built:** `cms/src/seed/demo-purge.ts` + `seed:demo:purge` npm script.

- **Dry run by default**; `--confirm` required to delete. Deliberate asymmetry — the operation
  is irreversible and a wrong match loses real editorial content.
- Removes **55 rows across 15 collections**: the demo content plus the reader rows that point at
  it (comments, poll votes, bookmarks, saved deadlines), children first.
- **Deliberately leaves alone:** the taxonomies (`categories`, `levels`, `districts` — real
  owner-approved data) and the **site logo** (`logo-placeholder-1.svg` in `media`).
- `demo.ts` now exports `DEMO_DEADLINE_TITLES` / `DEMO_QUIZ_TITLE` / `DEMO_POLL_QUESTION` —
  those three collections carry no `demo-` marker, so purge and seed share one source of truth.
- Post-purge leftover report so a row the matcher missed is visible, not silent.

**Verification method (reusable):** copied `cms/data/` (DB **and** media — Payload deletes upload
files from disk) to `/tmp`, then ran against the copy via `DATABASE_URI` + `MEDIA_UPLOAD_DIR`.
Proved: dry run → 55 reported; confirm → 55 deleted, taxonomies + logo intact; second run → clean
no-op; `seed:demo` → all 55 recreated; confirm again → 55 deleted. The dev DB was never touched
(verified by row counts + `PRAGMA integrity_check`).

**Two bugs the tests caught:**
1. The demo-author guard asked "does any article reference this author?" — always true on a dry
   run, because the demo articles are still present. Fixed by excluding the exact ids already
   scheduled for deletion (`id: { not_in: articleIds }`). A nested `and` with `slug: { not_like }`
   silently did not filter, which is why the id-based form was chosen.
2. The leftover report omitted `media`, so it claimed "every content collection is empty" while
   the site logo remained. Added `media` to the list with an explanatory line.

Lint delta: **0** (4 errors / 13 warnings both before and after — all pre-existing).

## Pipeline verification — "is the project ready to deploy?"

Re-derived the answer from the real repo instead of trusting the audit's §2b table. Found **four
defects in the pipeline** (not the site), three of them introduced by the Cloudflare removal.
Full write-up: `.sps/production-readiness-audit-2026-09-14.md` §6.

### 1. The lint gate was red (blocking)
§2b claimed "0 errors, 10 warnings". It was **4 errors** → `ci.yml` failed on every push.
Three were pure formatting (`SiteSettings.ts`, `verify-build-output.mjs`, `verify-csp-routes.mjs`)
— all from the Cloudflare commits. The fourth was `noAssignInExpressions`
(`while ((m = re.exec(t)) !== null)`), replaced with `t.matchAll(re)`.
**Lesson: a verification table is valid only for the revision it was taken against.**

### 2. CI could never pass (blocking)
`ci.yml` built the frontend with **no CMS**, so `CMS_URL` fell back to localhost, nothing
answered, and the build **exited 0 while emitting 32 pages instead of 84** — the thin-build
false green. The harnesses then failed on missing articles.

Measured both ways:

| Condition | build exit | HTML files | verify:csp | verify:build-output |
|---|---|---|---|---|
| No CMS (as CI was) | 0 | **32** | ❌ | ❌ |
| Seeded CMS (now) | 0 | **84** | ✅ | ✅ |

Fix: CI seeds the DB (`seed` + `seed:demo`) and runs the build inside `scripts/with-cms.sh`.

### 3. deploy.yml would have shipped a thin site (blocking)
It set `PUBLIC_CMS_ORIGIN` but **not `CMS_URL`**.

**⚠️ The two variables are different and easy to confuse:**
- `CMS_URL` — read at **build** time; all content is fetched from it. Must be reachable at build.
- `PUBLIC_CMS_ORIGIN` — the **browser-facing** origin for the interactive islands. Empty ⇒ they
  self-hide.

Setting only the latter yields a green 32-page build. Now both are set and documented.

### 4. A harness check was vacuous (minor)
`verify-build-output.mjs` searched `.htaccess` raw text for the literal `/article/*`. That string
was valid in the retired Cloudflare `_headers` format but cannot appear in Apache **regex** form
(a stale rule reads `^/article/.*`) — so the check could not fail. It also tripped on its own
documentation prose. Fixed by stripping comments, extracting `<LocationMatch>` patterns, and
checking those. **Counter-proved**: injecting `<LocationMatch "^/article/.*">` now fails it.

### 5. Stale Cloudflare refs (minor)
`frontend/.env.example` (Cloudflare proxy text, `_headers`) and `frontend/astro.config.mjs`
(`_headers`). Both fixed.

### Verified after the fixes
`lint` 0 · `typecheck` 0 · full build 84 pages · `verify:csp` 0 · `verify:build-output` 0 ·
whole CI sequence simulated end to end (seed → build → harnesses) all exit 0.

**Not deployable yet — but nothing agent-side is left.** Remaining blockers are owner-only:

## §2.2 image budget — closed (commit `2fa6db2`)

The last significant open audit item. Two defects, neither of them tuning.

**Measured before** (8 category archetypes — the hero on every article page):
```
AVIF  46 files | max  71.8 KB | >80KB  0 | >150KB 0
WebP  46 files | max 146.2 KB | >80KB  5 | >150KB 0
JPG   54 files | max 226.5 KB | >80KB 16 | >150KB 6   <- over budget
```

1. **`<Picture>` was emitting the source JPEG as its `<img>` element.** Unset, `fallbackFormat`
   defaults to the source format → a 226.5 KB JPEG, the heaviest asset on the site, on the path
   taken by exactly the devices the budget protects. Fixed with `fallbackFormat="webp"` in
   `CategoryImage.astro` (the only `<Picture>` in the codebase).
2. **Sources were 1376 px wide while the largest declared width was 1200.** Astro generates the
   fallback at the **source** width → a 1376 px file no `srcset` entry could match, 13% more
   pixels than the site ever serves. Downscaled the 8 sources to 1200×670 (repo 6.2 MB → 1.2 MB).

**Measured after:**
```
AVIF  46 files | max  71.2 KB | >80KB 0 | >150KB 0
WebP  46 files | max 137.9 KB | >80KB 4 | >150KB 0
JPG   removed entirely
```
The 4 WebP files over 80 KB are all **1200 px wide** — the hero tier, governed by the 150 KB row.
**Every image is within budget**; shipped image files fell 146 → 92.

⚠️ **Invariant recorded in `docs/image-optimization.md`: never ship a source wider than the
largest width you declare.**

### Made reusable — new skill `docs-consistency-audit`

The method above found 7 real defects, so it is now a skill rather than a memory note:
`~/.workbuddy-ai/skills/docs-consistency-audit/` — `SKILL.md` (the six classes, the method, why
it works) plus `scripts/audit.py` (runnable, repo-agnostic, `--class files,scripts,env,counts,dupes,meta`).

Two things the script's own development proved, both now documented in it:

1. **Restrict bare `pnpm <word>` to command position.** Matching it anywhere flags prose —
   "a pnpm monorepo", "the npm registry" — and buried the real findings under 23 false positives.
   Explicit `run`/`--filter` forms can match anywhere; the bare form cannot.
2. **Resolve workspace-relative paths.** A monorepo doc often writes `src/seed/purge.ts` rather
   than `cms/src/seed/purge.ts`. Checking only the repo root reports it missing. Resolving against
   every manifest-owning directory removed that class entirely.

Validated against this repo: files → 2 candidates (both intentional absences, now self-explaining);
scripts → clean; dupes → correctly hashes the three rule mirrors as identical; env → clean with an
allow-list.

**Exit code is 1 when anything is reported**, so it can gate a build.
