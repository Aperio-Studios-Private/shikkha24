## Pipeline verification — "is the project ready to deploy?"

Re-derived the answer from the real repo instead of trusting the audit's §2b table. Found **four
defects in the pipeline** (not the site), three of them introduced by the Cloudflare removal.
Full write-up: `.sps/production-readiness-audit-2026-09-14.md` §6.

### 1. The lint gate was red (blocking)
§2b claimed "0 errors, 10 warnings". It was **4 errors** → `ci.yml` failed on every push.
Three were pure formatting (`SiteSettings.ts`, `verify-build-output.mjs`, `verify-csp-routes.mjs`)
— all from the Cloudflare commits. The fourth was `noAssignInExpressions`
(`while ((m = re.exec(t)) !== null)`), replaced with `t.matchAll(re)`.
**Lesson: a verification table is valid only for the revision it was taken against.**

### 2. CI could never pass (blocking)
`ci.yml` built the frontend with **no CMS**, so `CMS_URL` fell back to localhost, nothing
answered, and the build **exited 0 while emitting 32 pages instead of 84** — the thin-build
false green. The harnesses then failed on missing articles.

Measured both ways:

| Condition | build exit | HTML files | verify:csp | verify:build-output |
|---|---|---|---|---|
| No CMS (as CI was) | 0 | **32** | ❌ | ❌ |
| Seeded CMS (now) | 0 | **84** | ✅ | ✅ |

Fix: CI seeds the DB (`seed` + `seed:demo`) and runs the build inside `scripts/with-cms.sh`.

### 3. deploy.yml would have shipped a thin site (blocking)
It set `PUBLIC_CMS_ORIGIN` but **not `CMS_URL`**.

**⚠️ The two variables are different and easy to confuse:**
- `CMS_URL` — read at **build** time; all content is fetched from it. Must be reachable at build.
- `PUBLIC_CMS_ORIGIN` — the **browser-facing** origin for the interactive islands. Empty ⇒ they
  self-hide.

Setting only the latter yields a green 32-page build. Now both are set and documented.

### 4. A harness check was vacuous (minor)
`verify-build-output.mjs` searched `.htaccess` raw text for the literal `/article/*`. That string
was valid in the retired Cloudflare `_headers` format but cannot appear in Apache **regex** form
(a stale rule reads `^/article/.*`) — so the check could not fail. It also tripped on its own
documentation prose. Fixed by stripping comments, extracting `<LocationMatch>` patterns, and
checking those. **Counter-proved**: injecting `<LocationMatch "^/article/.*">` now fails it.

### 5. Stale Cloudflare refs (minor)
`frontend/.env.example` (Cloudflare proxy text, `_headers`) and `frontend/astro.config.mjs`
(`_headers`). Both fixed.

## §2.2 image budget — closed (commit `2fa6db2`)

The last significant open audit item. Two defects, neither of them tuning.

**Measured before** (8 category archetypes — the hero on every article page):
```
AVIF  46 files | max  71.8 KB | >80KB  0 | >150KB 0
WebP  46 files | max 146.2 KB | >80KB  5 | >150KB 0
JPG   54 files | max 226.5 KB | >80KB 16 | >150KB 6   <- over budget
```

1. **`<Picture>` was emitting the source JPEG as its `<img>` element.** Unset, `fallbackFormat`
   defaults to the source format → a 226.5 KB JPEG, the heaviest asset on the site, on the path
   taken by exactly the devices the budget protects. Fixed with `fallbackFormat="webp"` in
   `CategoryImage.astro` (the only `<Picture>` in the codebase).
2. **Sources were 1376 px wide while the largest declared width was 1200.** Astro generates the
   fallback at the **source** width → a 1376 px file no `srcset` entry could match, 13% more
   pixels than the site ever serves. Downscaled the 8 sources to 1200×670 (repo 6.2 MB → 1.2 MB).

**Measured after:**
```
AVIF  46 files | max  71.2 KB | >80KB 0 | >150KB 0
WebP  46 files | max 137.9 KB | >80KB 4 | >150KB 0
JPG   removed entirely
```
The 4 WebP files over 80 KB are all **1200 px wide** — the hero tier, governed by the 150 KB row.
**Every image is within budget**; shipped image files fell 146 → 92.

⚠️ **Invariant recorded in `docs/image-optimization.md`: never ship a source wider than the
largest width you declare.**

### ⚠️ The first CI run FAILED at lint — while local lint passed with exit 0

That single failure justified the whole exercise. Root cause, and it was **my own mistake**:

I removed the `.wrangler/` entry from `.gitignore` (tidying Cloudflare residue). That made the
directory no longer ignored, so the same commit's `git add -A` **tracked it** — a stale Cloudflare
cache containing an account id and an email. CI then failed on it:

```
.wrangler/cache/wrangler-account.json format   → exit 1
```

**Two lessons, both worth keeping:**

1. **Removing a `.gitignore` entry changes what Biome scans.** It is not a config-only file — it
   decides which files the linter sees. The local verification run happened *before* that edit, so
   my evidence was invalidated by my own later change and I did not re-run lint.
   **Rule: after touching `.gitignore`, re-run lint.**
2. **"Verified by local simulation" was not good enough, and saying so was the right call.** Every
   local gate passed; real CI failed on the first run. Local verification cannot catch what only
   the checkout-and-scan environment reveals.

### Fixed properly

No credential was exposed — an account id and an email, and the email is already in every commit's
author field. The repo was private, one collaborator, minutes old, so rather than leave it in
history I rewrote the bad commit out (`git reset --soft HEAD~1`, restore, recommit,
`--force-with-lease`). Verified: **no wrangler path anywhere in the remote tree**, 311 files.

The `.gitignore` entry stays, but under an honest heading — it is not a Cloudflare dependency, it
is a guard against a stale cache in a clone that predates the removal. Dropping it would re-break
the lint gate for anyone whose tree still has one.

### Process fix

`gh run watch --exit-status` + `gh run view --log-failed` gave the real error in one step. From now
on: **push first, then verify on the runner** — a green local run is a hypothesis, not evidence.

### 🚨 Launch-blocking `.htaccess` defect found and fixed (17:10+06:00)

Re-verifying the tree after the CI-action merges turned up a **total-outage** defect that
had survived the whole S12 sweep.

**What was wrong.** `frontend/public/.htaccess` dispatched the CSP profiles with
`<LocationMatch>`. Apache permits `<Location>`/`<LocationMatch>` in **server and virtual-host
context only**; in `.htaccess` it is a core parser error. Proven locally by serving the file
through the machine's own Apache 2.4.67:

```
[core:alert] .htaccess: <LocationMatch not allowed here
→ HTTP 500 on every single request
```

Deploying it would have taken the **whole site down**, not merely blocked AdSense.

**Two cache rules were dead for the same class of reason.** `<FilesMatch>` matches the
**basename**, not the path, so `<FilesMatch "\._astro/">` and `<FilesMatch "^/fonts/">` never
matched a file — hashed assets and self-hosted fonts shipped with **no `Cache-Control`**.
`<FilesMatch "\.html$">` is a genuine basename rule and was fine.

**Why nothing caught it.** `scripts/verify-csp-routes.mjs` parsed the `<LocationMatch>` blocks
and **reimplemented Apache's regex matching in JavaScript**. It validated the rules' intent and
never asked Apache whether the file was even legal. It passed for three days. The release-readiness
sweep had also recorded this check as "production-only" and moved on — which was simply false,
since `apachectl`/`httpd` was already installed.

**The fix.** Dispatch is now `SetEnvIf Request_URI` + `Header ... env=`; cache rules use the same
mechanism. Both are `FileInfo`-level overrides, which is what a cPanel host grants. **All three CSP
strings preserved byte-for-byte** — policy unchanged, only the mechanism.

**New harness:** `scripts/verify-apache.mjs` (16/16) starts a **real Apache** over the real `dist/`
and asserts status, CSP header count, and each page's profile — deriving the expectation from the
page's own JSON-LD (`NewsArticle` / `CollectionPage` / `LiveBlogPosting`) so it cannot share the
rule's blind spots. Wired into `pnpm verify`, `ci.yml`, `deploy.yml`. The old harness is deleted.

**It caught a second defect on its first run:** the first rewrite excluded a hand-written list of
"reserved" first segments, including `study-abroad` — which is both a 2-segment listing *and* the
first segment of real article URLs (`/study-abroad/4/demo-study-abroad-canada`). Every
study-abroad article silently fell to the strict profile. The list is gone; the rule is structural.

**S12 items 11 and 12 are now closed locally** (previously listed as production-only).

FAIL  every built page: no 5xx, one CSP header, correct profile

relaxing `/latest` notes and passes.

three-segment path, and `/latest/page/2` is three segments — so page 2 of the feed would have
been served the *article* profile (relaxed, `frame-src` open for video embeds) with no ads on
it. Rule now excludes a middle segment of `page`:

```
^/[^/?#]+/(?!page/)[^/?#]+/[^/?#]+/?(\?.*)?$
```

A negative lookahead is fine in `mod_setenvif` (PCRE) — verified by running Apache, not by
reading docs. New check pins it.

**New gate: `verify:links`.** Every internal `href`/`src` in `dist/` must resolve to a built
file — **4,189 links, 84 pages**. Nothing checked this before: Astro does not resolve `href`

**Final state:** build exit 0, **84 pages**; `verify:apache` 18/18, `verify:build-output`
24/24, `verify:links` 3/3; lint 0 errors, typecheck clean. Confirmed the build *regenerates*

fire at all**: every raster upload is re-encoded to WebP, so a stored file is always
`image/webp`/`image/svg+xml`, both allowed. Kept as defence-in-depth, documented as such.
