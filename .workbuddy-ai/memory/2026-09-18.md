### 🚨 Four defects found and fixed

1. **A reporter could publish their own article** (launch-blocking). `Articles`
   claimed collection `update` kept publishing to editors. It does not —
   `update: isEditorial` must include reporters so they can save drafts, and
   `_status` had **no field guard**. `PATCH {"_status":"published"}` published
   unreviewed content. Fixed with `guardPublishStatus`, which **throws** (a
   stripped write returns 200 and the reporter believes it went live).
   *Found because the harness asserted the opposite and failed.*

2. **`isSelfOrAdmin` cannot be used on `authors`.** It compares the document id
   to the **user** id — right for `users`, wrong here (`Users.authorProfile →
   authors`). A reporter got a flat 403 editing their own profile while the
   comment claimed the opposite. → `isOwnAuthorProfileOrEditor`.

3. **The 2026-09-16 timezone fix had shipped two broken imports.**
   `CommentSection.astro` and `DeadlineStrip.astro` called `formatBnBd` without
   importing it. **`tsc` never checks `.astro` frontmatter** (`@astrojs/check`
   rejects TS 7 — why Biome was adopted), so it is neither a type nor a lint
   error; the thin build passed because both components self-hide without a CMS.
   → new gate **`pnpm verify:astro-imports`**, counter-proved.

4. **`reporterId` was never backfilled.** Hook ran on create only, so authors
   predating S13 would never get an ID. Now assigns on any save where absent.

Also: the harness **polluted the DB it tested** (3 crashes → 20 orphan rows → real
`/reporters/verify-a-…` pages in `dist/`). Cleanup moved to `finally` + startup
purge of the reserved `verify-` namespace.

## Footer: developer credit + official social links (commit `06c9383`)

Owner asked for two things: the developer's WhatsApp/Facebook were styled like
the site's own contact links, and the footer had "no option" for the portal's
official social accounts.

**1. Developer credit** → new `DeveloperCredit.astro`, the **last** band.
Was a bordered/shadowed button group with 32px controls and 16px icons — the
heaviest element in the footer, louder than the copyright. Now: one line, 11px,
inline links, no chrome, labelled `ডেভেলপার:`.
⚠️ Colour is **`ink-muted`, not `ink-subtle`** — `#8a8a8a` on white is ~3.5:1 and
**fails WCAG AA 4.5:1** at 11px; `#5a5a5a` is ~7.5:1. Subordination comes from
size + absence of chrome, not from washing the text out.

**2. Official social links — the real finding.** Three surfaces derived the list
**independently**:
- Footer column 4: its own `SOCIAL_META` map (Bengali labels + icons)
- Header: `Object.entries` and rendered **the raw field name** as the label —
  the literal string `facebook`, lowercase English, in a Bengali-only UI
- Homepage JSON-LD `sameAs`: `Object.values` with **no validation**

…while a comment claimed they "cannot drift".

🚨 **None of the three validated the URL scheme.** CMS text → straight into
`href`. Astro escapes the attribute (no tag breakout) but **escaping does not
neutralise a scheme**, so a stored `javascript:` URL would execute on click, on
our own origin.

Fixed: `lib/social.ts` (Bengali labels, fixed order, **http/https-only**) +
`SocialLinks.astro` (header / drawer / footer variants). Removed the footer's
duplicate block, its dead `SOCIAL_META`, the header's raw-key loop, and the
JSON-LD's `Object.values`.

**Counter-proved end to end:** stored a real `javascript:alert(document.domain)`
and a malformed `not a url at all` in the CMS, built, and confirmed **no
`javascript:` anywhere** — not in an href, not in `sameAs` — while the valid URLs
still reached all three surfaces. 12/12. Test values then **cleared** (shipping
invented `shikkha24` handles could point readers at a stranger's page).

**⚠️ Owner action:** set the real accounts at `/admin → Site Settings →
সোশ্যাল লিংক`. The block self-hides until then.

**Also learned:** the footer *already had* a working social block — I added a
second one before reading the whole file. **Read the whole component before
adding to it.**

**Build note:** `CMS_URL=http://localhost:3000`, so a plain `build:frontend` is a
**34-page thin build**. Use `scripts/with-cms.sh bash -c "pnpm run build:frontend"`
for a real **147-page** build. The 2 `verify:build-output` failures ("articles
built", "legacy redirect stubs") are the thin-build signature, not a defect.

## ⚠️ "CMS changes don't show on the site" — the two causes (commit `7daab22`)

Owner added social links in `/admin` and reported they "are not showing in the
footer or anywhere". **Two causes, and the first one is architectural, not a bug.**

### Cause 1 — the frontend is static; a CMS edit does not change it

The CMS is read **at build time only**. Editing `/admin` changes the database and
nothing else. A rebuild is what publishes it.

- Locally: `scripts/with-cms.sh bash -c "pnpm run build:frontend"`
- Production: **`DEPLOY_WEBHOOK_URL` must be set** — it is currently **unset**, so
  nothing triggers a rebuild automatically. Verified in `cms/.env`.

After a rebuild all four links render — footer, header ribbon, mobile drawer and
JSON-LD `sameAs`. **The rendering was never broken.**

⚠️ **This is the single most likely owner confusion in this project.** Whenever
the owner says "I changed it in the CMS and nothing happened", check the build
first, not the code.

### Cause 2 — the field accepted the wrong thing (a real defect)

Stored values were the **platforms' own front pages**:

```
facebook  -> https://www.fb.com/          youtube   -> https://www.youtube.com/
instagram -> https://www.instagram.com/   twitter   -> http://x.com/
```

All **valid absolute URLs** → passed every check, rendered fine, and sent readers
to Facebook's homepage instead of the newsroom's page. The JSON-LD published four
meaningless `sameAs` entries. Nothing a test could see.

Fixed: `cms/src/lib/social-url.ts` rejects a bare handle, a missing scheme, plain
`http`, and specifically a **bare platform homepage**; `SiteSettings` gained a
Bengali admin description; errors name the mistake and show a worked example.
Counter-proved with 11 checks (`cms/src/verify/social-url.ts` → `verify:social`),
asserting **both** the rejections and the acceptances — a validator that rejected
everything would pass every negative case while being useless.

**Rule of thumb:** when a CMS field feeds an `href`, validate that it *identifies
the thing intended*, not merely that it parses as a URL.
