## Fix: featured image missing on the article detail page

### Root cause
`frontend/src/pages/article/[slug].astro` rendered the hero only when
`article.featuredImage` resolved to a populated media object, and had **no
fallback**. `ArticleCard.astro` has always fallen back to the category
archetype (`getCategoryImage()` + `<CategoryImage>`), so a story with no photo
of its own showed its archetype on every homepage card but nothing at all on
its own page.

Verified against the live CMS: **0 of 12 published articles have a
`featuredImage`** — so this affected *every* article page, not an edge case.
Built output confirmed it: 0 of 12 article pages contained a hero block.

### Fix (one file)
- Resolve the hero with the same shared helper the cards use —
  `resolveCmsImage(article.featuredImage, article.title)` — and fall back to
  `<CategoryImage image={categoryImage} priority />` when it returns null.
- Dropped the hand-rolled `PUBLIC_MEDIA_BASE_URL` string concat in favour of
  `mediaUrl()` (so an already-absolute CMS url is not double-prefixed) and got
  a real `srcset` + true dimensions instead of the hard-coded 1200×675 box.
- Wrapper reserves `aspect-16/9`; hero is `loading="eager"` +
  `fetchpriority="high"` because it is the LCP element.

## S12 follow-up — ⚠️ CSP route regression found and fixed

### The bug
The S11 URL change moved articles from `/article/:slug` to
`/:category/:id/:slug`, but `frontend/public/_headers` still had the relaxed-CSP
rule as `/article/*`. It matched **no article page** → every article would have
fallen to the strict CSP in production, blocking AdSense and the video-embed
`frame-src`, silently (Cloudflare applies the policy; nothing local shows it).
Same failure class as the S8 site-wide CSP bug.

### Why a splat cannot fix it (Cloudflare `_headers` semantics, verified via docs)
- `*` splat matches greedily and **crosses `/`**; only **ONE splat per rule** →
  `/*/*/*` is invalid.
- `:name` placeholder matches all chars **except `/`** → exactly one segment.
- An article URL shares no literal prefix with its category listing, so no
  prefix rule can express it. Fix: placeholder pattern `/:category/:id/:slug`.

### The fix
- `frontend/public/_headers`: `/article/*` → `/:category/:id/:slug` (same relaxed
  CSP value, incl. `frame-src` for youtube-nocookie). `/article/:slug` redirect
  stubs now deliberately keep the strict profile.
- Added two production checks to the header comment (detach + placeholder match).
- `docs/security.md` §5: added the relaxed route table, the placeholder warning,
  and fixed the stale "R2 domain" reference (media is on the CMS host since S9).
- Three CMS comments updated (`blocks/editors.ts`, `blocks/VideoEmbedBlock.ts`,
  `collections/Articles.ts`) so nobody "restores" the dead `/article/*` prefix.

### Verification
- New harness `scripts/verify-csp-routes.mjs` — reimplements the documented
  `_headers` matching semantics and asserts against the real built paths.
  18/18 pass. Wired into `pnpm verify` (after build).
- Counter-proof: matcher vs old pattern `/article/*` on a real article path →
  `false`; new pattern → `true`. The harness genuinely fails on the old rule.
- Frontend + CMS `tsc --noEmit`: exit 0. Build: 79 pages.

### Lesson
**A URL architecture change is a cross-cutting change.** The routes are not the
only thing keyed to the URL shape — CSP rules, sitemaps, feeds and canonical
tags all encode it. Grep for the old prefix after any URL change.

### Process finding — build must go through the package script
Several verification runs in this session used `npx astro build` directly, which
**skips the `&& pagefind --site dist` half** of `frontend`'s `build` script. The
resulting `dist/` looked complete (79 pages, all routes) but had **no search

## CMS sync investigation — one real bug, one contract gap

Reported: "CMS data is not syncing properly."

### Method
Split the problem into the two directions data actually moves, then verified each:
- **read path** = build-time CMS fetch → static pages
- **write path** = reader submissions → CMS

### Read path — was already correct
Wrote `scripts/verify-cms-sync.mjs`: for each listed collection, assert every
record's identifying string appears in the built page. 8/8 collections pass
(articles 12/12, categories 8/8, scholarships 4/4, result-links 3/3,
study-abroad 8/8, institutions 5/5, circulars 3/3, deadlines 5/5).
Detail pages also verified (study-abroad guide fields present).

### Write path — one genuine bug
`POST /api/comments/submit` returned **404**. Root cause: the endpoint was
registered at the API root with `path: '/comments/submit'`, and **`comments` is a
collection slug** — so Payload's collection router claimed `/api/comments/*`
first and parsed `submit` as a document ID. The handler was never reached.
Every reader comment submission was failing.

Proof: `GET /api/comments/submit` produced a `comments where id = 'submit'`
query (the `NaN` error in the CMS log) — the collection router, not our handler.

**Fix:** mount on the Comments collection with a collection-relative path
(`path: '/submit'`). Resolves to the SAME public URL, and collection endpoints
are matched before the collection's generated routes (proven by the poll vote
endpoint working). Removed from the root `endpoints` array.

### Second gap — newsletter form could not work
`NewsletterSignup` gated only on a CMS origin. But the subscribe endpoint
refuses with **503** when no mail transport is configured (deliberate: accepting
an address that can never be mailed is a lie). So the footer showed a subscribe
box that always errored — the S8 "no control that cannot work" rule violated by
a precondition the frontend couldn't see.

**Fix:** added `getNewsletterStatus()` (fails closed), resolved once per build in
`Footer.astro`, passed to the component as an `enabled` prop.
Verified BOTH directions: absent with no SMTP, present with SMTP.

### Not bugs (verified as correct)
- `push/subscribe` → 503 when VAPID unset. `DeadlineReminder` already self-hides
  via `isEnabled('push') && pushConfigured() && cmsOrigin && remindAt`.
- Poll vote: my first test read `option.votes`; the field is `voteCount`. And the
  duplicate guard returns `alreadyVoted: true` with 200, not an error. Endpoint
  was fine; the test was wrong.

### Methodological trap (cost me a wrong conclusion)
An early probe sent **GET** to every endpoint and concluded five were missing.
Wrong: a POST-only route answers GET with **404**, so "missing" and "wrong
method" are indistinguishable. **Always probe with the method the client uses.**

### New harnesses
- `scripts/verify-cms-sync.mjs` — read path (needs CMS up + dist built)
- `cms/src/verify/endpoints.ts` — write path (real HTTP write → read back via
  local API → cleanup). Wired as `verify:endpoints`.
The existing S9 harnesses all used the Payload **local API** and never touched
the HTTP routing layer — which is exactly where the collision lived.
