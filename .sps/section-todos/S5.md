## Fixed 2026-09-15: `/latest` pagination was broken, and nothing could see it

`pages/latest.astro` was a single page that read `?page=N` from the URL. On a
static build `Astro.url.searchParams` is evaluated **at build time**, where there
is no query string — so `page` was always 1 and every page rendered the same
twelve articles. Meanwhile `Pagination` builds its links as `${basePath}/page/${n}`
— path segments, not a query string — and **no route emitted `/latest/page/2`**.
The moment a thirteenth article was published, `/latest` would have rendered a
"পরের →" link pointing at a 404.

It was invisible because the demo corpus held **exactly** twelve articles and
`PAGE_SIZE` is 12, so `totalPages` was always 1 and the control never rendered.
The same corpus boundary also hid a CSP defect: the article rule matched any
three-segment path, and `/latest/page/2` is three segments, so page 2 would have
been served the *article* profile (relaxed, with `frame-src` for video embeds)
despite carrying no ad slot. See M17.

Now `pages/latest/[...path].astro` — the same catch-all shape the category route
uses, so listing behaviour lives in one place — and `scripts/verify-links.mjs`
checks every internal link in the built output, so this class cannot return
quietly.

## Two design notes

**Breadcrumbs generate the visible trail and the JSON-LD from one array.** A
breadcrumb that shows one thing to the reader and tells Google another is worse
than no breadcrumb. Sharing the source makes drift impossible.

**`getStaticPaths` fetches page 1 to learn the page count, then emits one path
per page.** Category pages therefore scale with content — a category with 300
articles emits 25 pages automatically.

## Author / tag / date archive — ✅ BUILT 2026-09-15

Deferred since 2026-09-12 for lack of content to show. The demo corpus was enlarged
the same day (see below), which removed that blocker, and the routes are now built:

| Route | File | Notes |
|---|---|---|
| `/tag/:slug`, `/tag/:slug/page/:n` | `pages/tag/[...path].astro` | `CollectionPage` + `BreadcrumbList` + `ItemList` |
| `/author/:slug`, `/author/:slug/page/:n` | `pages/author/[...path].astro` | `ProfilePage` wrapping a `Person`; shows photo, designation, bio |
| `/archive`, `/archive/:year-month`, `/archive/:year-month/page/:n` | `pages/archive/[...path].astro` | Index of months + month listings. Buckets derived from published articles, never stored |

Supporting changes: `getTags()` / `getAuthors()` added to `lib/cms.ts` (a static
build needs every slug up front); `relationEntries()` added so a tag chip can carry
both a Bengali label and a slug; all three route types added to `sitemap.xml`
(**47 → 81 entries**).

**Wired so they are not orphans** — a route nothing links to is a route no reader
finds, and `verify:links` cannot check it either:

- article byline → `/author/:slug`
- article footer → a tag row linking each tag
- `/latest` header → `/archive`

**Two defects fixed on the way:**

1. **The article JSON-LD advertised a URL that 404'd.** `Person.url` pointed at
   `/author/:slug`, which did not exist. It also had a **double slash** —
   `${siteUrl}/author/…` where `Astro.site.href` already ends in `/`, producing
   `https://shikkha24.com//author/demo-reporter`. `verify:links` never saw it
   because JSON-LD uses `"url":"…"`, not `href=`. Fixed with `new URL(...)`.
2. **Dead code in all five listing routes.** `parsePath()` was defined in
   `category`, `latest`, `tag`, `author` and `archive` and **never called** — the
   props come from `getStaticPaths`. Removed from all five.

**⚠️ The archive month is ONE path segment (`/archive/2026-09`), deliberately.**
`/archive/2026/09` would be a three-segment path, and the `.htaccess` article rule
matches any three-segment path — so it would have been served the *article* CSP
profile despite carrying no ad slot. One segment avoids the collision structurally
rather than adding another exclusion to the rule (the M15 enumeration trap).
`pnpm verify:apache` confirms all three route types are correctly **strict**.

**⚠️ Pagination on these routes is implemented but not exercised by the current
corpus.** No tag, author or month holds more than `PAGE_SIZE` articles, so none of
them emits a `page/2`. The mechanism is the same `getStaticPaths` → `Pagination`
pattern that `/latest` now genuinely exercises (24 articles, 2 pages), but these
particular page-2 routes have never been generated. Stated plainly rather than
implied covered — M17.

## The corpus was too small to exercise the code (fixed 2026-09-15)

`PAGE_SIZE` is 12 and the corpus held **exactly** 12 articles, so `totalPages` was
always 1 and **no pagination control ever rendered anywhere**. Two defects hid
behind that — a `/latest` route that read `?page=N` at build time and would have
404'd its own page-2 link, and a CSP rule that tagged `/latest/page/:n` as an
article. Both are fixed; see M17.

The corpus is now **24 articles**, so `/latest` emits two pages, and the seed also
gained the content the deferred routes above were waiting for:

| Added | Why |
|---|---|
| 12 more articles (24 total) | Exceeds `PAGE_SIZE`, so pagination is actually generated |
| `tags` on articles + 14 demo tags | Gives tag pages something to list |
| 3 demo authors (was 1) | Gives author profiles something to list |
| Publish dates ~4 days apart (~3 months) | Gives the date archive real month buckets |

⚠️ **`seed:demo:purge` was updated to match.** It previously purged exactly one
hardcoded author slug, so two of the three new authors would have survived a
purge; and `tags` was absent from the purge list entirely, so every demo tag
would have survived. Both are now pattern-matched on `demo-`.

**Subcategory filters** render when a category has children via the
`categories.parent` self-relation. They are correctly empty under the approved
flat tree — the mechanism exists for editors who add children later.
