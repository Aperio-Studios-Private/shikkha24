## What was built

### N1 — Scholarship tracker (`/scholarships`)

Deadline-sorted list of active scholarships, soonest first. Each entry shows:
funding-type badge, international badge, level name, country, amount, eligibility,
apply link. Urgency labels (আজ / আগামীকাল / N দিন বাকি) for unmissable
deadlines. JSON-LD `ItemList`, breadcrumbs, empty state.

### N2 — Academic calendar enhancement (`/deadlines`)

The existing `/deadlines` page gained **client-side filtering**: type chips
(সব / ভর্তি / ফলাফল / পরীক্ষার রুটিন / বৃত্তির সময়সীমা / ছুটি / বিজ্ঞপ্তি),
a level dropdown, and a district dropdown. Each deadline `<li>` carries
`data-type`, `data-level`, `data-district` attributes; the component script
(emitted as an external hashed file) toggles `hidden` on filter change. A
"no results" message appears when all items are hidden. With JavaScript off,
all deadlines are visible — the filter is progressive enhancement, not a gate.

### N3 — Results & merit lists hub (`/results`)

Published result links sorted by `publicationDate`, newest first. Each shows
exam name, board/institution, publication date, official URL, and merit-list
URL. JSON-LD `ItemList`, breadcrumbs, empty state.

### N4 — Institution directory (`/institutions` + `/institutions/[slug]`)

Hub: grid layout with type badges (পাবলিক / বেসরকারি) and verified checkmark.
Detail: info table (district, established, levels offered, website), address,
richText description. `getStaticPaths` from `getAllInstitutionSlugs()`.
JSON-LD `CollegeOrUniversity`. 404 redirect on missing institution.

### N5 — Exam routine hub (`/exams`)

Filtered view of Deadlines with `type === 'examRoutine'`, soonest first. Reuses
`getAllDeadlines()` from `cms.ts` and filters client-side — the data set is
small (50 max), so no new fetch function was added to the already-740-line
`cms.ts`. Shows urgency labels, same pattern as `/deadlines`.

### N6 — GPA calculator (`/gpa`)

Flag-gated (`PUBLIC_FLAG_GPA_CALCULATOR`), client-side, zero backend. SSC/HSC
grading system (80+: A+ 5.00, 70–79: A 4.00, 60–69: A− 3.50, 50–59: B 3.00,
40–49: C 2.00, 33–39: D 1.00, 0–32: F 0.00). Table with subject name, marks,
grade, optional checkbox. Real-time calculation, add-row button. `<noscript>`
fallback message.

#### 🚨 Corrected 2026-09-28 — the rule below was wrong, and this file recorded it as the design

> ~~Optional subject's points are capped at 2.0 when added to the main subject
> sum, divided by main subject count.~~

That sentence is the **bug**, written down as intent — which is why nobody
questioned it. The real rule, verified against three independent sources before
the fix (see `.sps/handoff.md`):

```
৪র্থ বিষয় বোনাস = সর্বোচ্চ(০, ৪র্থ বিষয়ের পয়েন্ট − ২.০০)
চূড়ান্ত জিপিএ = (মূল বিষয়ের পয়েন্টের যোগফল + বোনাস) ÷ মূল বিষয়ের সংখ্যা   [সর্বোচ্চ ৫.০০]
```

Only the part **above** 2.00 is added, and the maximum bonus is therefore
**3.00**, not 2.00. Three defects were fixed together:

1. **The 4th-subject bonus** used `min(GP, 2)` instead of `max(0, GP − 2)` — an A+
   4th subject contributed 2.00 instead of 3.00.
2. **An F in a compulsory subject** scored 0.00 for that subject instead of
   zeroing the whole result. It is a hard 0.00, however good the others are.
3. **The final letter grade** was looked up against the **marks** boundaries
   (80, 70, 60 …) rather than the grade points (5.00, 4.00, 3.50 …), so every
   result was labelled **এফ** — the only boundary a GPA can satisfy is 0.

Also fixed: the rule text claimed a maximum bonus of 2.00; `ঐচ্ছিক (৪র্থ/৫ম)`
implied a 5th optional subject that does not exist; and the marks input capped at
100, so the **200-mark combined Bangla and English** papers could not be entered.

⚠️ **The root cause is structural, not arithmetic:** the calculation lived inside
a page `<script>`, so *nothing could call it* and nothing could check it. It is
now `frontend/src/lib/gpa.ts` — a pure module — with `pnpm verify:gpa` over it
(60+ checks, including the three worked examples that expose the old bugs), wired
into `pnpm verify` and CI. `verify:build-output` additionally asserts the page's
DOM contract, so a renamed element id cannot silently kill the calculator.

## Architecture decisions

### Content pages are ungated; only the GPA calculator is flag-gated

The 6 content pages (scholarships, results, institutions, circulars,
study-abroad, exams) follow the `/deadlines` pattern — no feature flag, always
rendered. The GPA calculator is a client-side tool (like the quiz), so it is
flag-gated on `PUBLIC_FLAG_GPA_CALCULATOR`. This matches the established
pattern: interactive tools are flag-gated, content pages are not.

### All data is editorially curated — no external API

Every S10 feature is backed by a Payload collection with editor-curated data:
Scholarships, Deadlines, Institutions, Circulars, Result Links, Study Abroad
Guides. No external API is needed for any of them (`docs/education-feature-inventory.md`
§4, `docs/data-sources.md` §2). The GATE check ("every data-backed element has
a confirmed free provider or is descoped") is therefore satisfied by
construction — there are no data-backed elements that need a provider.

### The exam hub reuses the Deadlines collection, not a new fetch

`/exams` filters `getAllDeadlines()` by `type === 'examRoutine'` client-side.
Adding a new fetch function to the already-740-line `cms.ts` would have been
unnecessary for a 50-item dataset. The data model already has the `type`
discriminator — N2 and N5 share it by design.

### The deadlines filter is progressive enhancement

With JavaScript disabled, all deadlines render unfiltered — the same
behaviour as before the enhancement. The type chips, level dropdown, and
district dropdown are inert without JS; no deadline is hidden by default.
The "no results" message is `hidden` by default and shown only by the script.
