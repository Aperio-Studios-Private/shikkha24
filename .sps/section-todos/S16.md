# S16 — Reader Reactions

**Status:** ✅ **BUILT 2026-09-28** · **Requested as:** the reaction half of feature #7
**Specification:** `docs/feature-batch-2.md` §5 · **Index:** `docs/feature-register.md`

⚠️ **Comments are already built** (S4 / S9). Only reactions were outstanding.

## What was built

### 1. `Reactions` collection — `cms/src/collections/Reactions.ts`

`article` · `type` (like / love / wow / sad / angry) · `reader` · `fingerprint`.

**Three decisions worth stating, because the field list alone does not convey them:**

- ⚠️ **`read` is NOT public.** A row holds a `fingerprint`. Making the collection publicly
  readable would let anyone page through every fingerprint on an article, and would ship the
  entire row set to every reader just to add up five numbers. The aggregate is computed
  server-side by `GET /api/reactions/counts`, which returns five counts and the caller's own
  choice and nothing else.
- ⚠️ **Dedupe is a database constraint, not a UI rule.** Two compound unique indexes, exactly
  as the spec requires:
  - `(article, type, reader)` — a signed-in reader is the same reader on every device.
  - `(article, type, fingerprint)` — an anonymous reader is recognised by the hashed IP + UA.

  **Both are needed.** SQLite treats `NULL` as distinct in a unique index, so the `reader`
  index cannot constrain an anonymous row at all — the fingerprint index carries that case,
  and the reader index is what survives a reader clearing their cookies.
- ⚠️ **Never wrapped in `withRebuildTrigger`.** Like comments and poll votes, these rows are
  written by the public. A reader tapping a reaction must never cost a CI rebuild — which is
  precisely why the counts are read at runtime.

### 2. Two endpoints — `cms/src/endpoints/reactions.ts`

`POST /api/reactions/toggle` and `GET /api/reactions/counts`, **both mounted on the
collection** with collection-relative paths. A root-mounted path whose first segment equals a
collection slug is swallowed by that collection's generated REST route and answers 404 —
exactly what happened to `/api/comments/submit` (`docs/security.md` §13.4).

**Toggle semantics: replace, not accumulate.** The island is a `radiogroup` — one reaction per
article — so choosing a different one replaces the previous, and tapping the current one
removes it. The endpoint deletes the caller's other rows before inserting.

**The write is whitelisted key by key.** `overrideAccess: true` is unavoidable (there is no CMS
user to run access control against), so the `fingerprint` is computed server-side from the
request and **never read from the body**.

**Two guards, in the same order as `comments.ts`:** honeypot (silent success, no write), then
per-IP rate limit (20 toggles / 5 min — generous, because a reader may genuinely change their
mind), then validation against the five-type allow-list.

⚠️ **The insert is wrapped in a `catch` that returns fresh counts rather than a 500.** Two
concurrent toggles from one browser can both see "no existing row" and both try to insert; the
unique index refusing the second is the database doing its job, not an error the reader caused.

⚠️ **`pagination: false` on the counts query is required, not cosmetic.** Payload's `find`
returns one page by default, so counting `docs.length` without it would silently cap the tally
at the page size — a wrong number that looks like a real one (`sandbox-build-traps` trap 10A).

### 3. `ReactionBar.astro` — the island

- **Self-hides** when `getPublicCmsOrigin()` is null, plus a `<noscript>` hide — the S8 rule.
- **Accessible as a `radiogroup`**: `role="radio"` buttons with `aria-checked`, roving
  `tabindex`, and arrow-key navigation. A native `<input type=radio>` cannot express
  "tap the current one to remove it", so the roles and the keyboard contract are carried by
  hand. Counts are `aria-hidden` and mirrored into a `role="status" aria-live="polite"` region.
- ⚠️ **No counts in the static HTML.** They are read at runtime, on the reader's first tap.
  Baking them in at build time would freeze them until the next rebuild, so a reader's own
  reaction would appear to do nothing. It also means the page makes **zero** requests for a
  reader who does not react.
- `localStorage` is used only to paint the control before the first request; the response's
  `mine` overwrites it. **The server is the authority.**
- Labels are **text, not emoji** — five Bengali labels, consistent with the site's typography.

**Counter-proofs:**

- ⚠️ **The counter-proof required a different method than expected, and this is the finding
  worth keeping.** Dropping the unique index out-of-band with `sqlite3` **cannot** work:
  `payload run` re-applies the declared schema on boot, so the index was silently recreated
  before the harness executed and the harness **passed with the index "dropped"** — a
  counter-proof that proved nothing. The honest method is to remove the index from the
  **collection config**: the schema push then drops it, and the harness reports
  `FAIL — the database refuses the SAME reaction twice … a second row was created — the unique
  index is missing`. Restored byte-identical, re-ran, green.
- **Both indexes are exercised separately**, and the harness provisions a temporary reader when
  the database has none — otherwise the `(article, type, reader)` half would be untested, and
  "untested" is exactly how a missing index survives.
- **The harness asserts the direction that matters**: it also checks that a *different*
  reaction type IS still allowed, so an over-broad index cannot pass as a working one.
- **The anonymous read is asserted to be refused** (Payload throws `Forbidden`; both that and
  an empty page are accepted, so the check tests the access rule and not a Payload detail).
- **The no-request invariant:** the island fetches only on tap, and `verify:build-output`
  asserts no counts reach the markup.

## Deviations & open items

- ⚠️ **Single-choice is an endpoint rule, not a database rule.** The spec specifies two
  compound indexes, and neither makes "one row per article per fingerprint" impossible — so a
  hand-crafted request could still record, say, a `like` **and** a `love` from one fingerprint
  and inflate the counts slightly. The UI cannot produce that state, and the rate limit bounds
  it. Making it a database rule would need two further unique indexes
  (`(article, reader)`, `(article, fingerprint)`), which the approved spec does not call for —
  recorded here rather than added silently (rule 13).
- ⚠️ **The vocabulary exists in three places** — `cms/src/lib/reactions.ts`,
  `cms/src/collections/Reactions.ts` (admin labels) and `frontend/src/lib/reactions.ts`. The CMS
  cannot be imported from the frontend (it pulls in `node:crypto` and Payload), and a shared
  package for five strings is more machinery than the problem deserves. **Grepping for `angry`
  finds all three.**
- ⚠️ **`Reactions.read` is editor-only, so the Payload admin list is the only way to inspect
  rows.** That is deliberate; if editors ever need a moderation view, it should be a custom
  view rather than opening the collection.
- The `verify:search-init` SKIP and the S13 `/admin/reporter` manual check remain outstanding
  and are unchanged by this section.
