## CMS reconciliation note (recorded 2026-09-12)

`sps-cms` v2.3.0 mandates a bespoke "visual builder" CMS (`/api/cms/submit-form`,
`data-sps-key` surface tagging, `cms.config.ts` polymorphic collections). The
**approved plan mandates Payload CMS 3.89.0** (`.sps/plan.md`, approved 2026-09-11).
Rule 13 forbids build/plan drift, so `sps-cms` is applied as a **set of principles**
inside Payload rather than as a replacement engine:

| sps-cms law | How it is satisfied in this project |
|---|---|
| 100% granular surface coverage (no hardcoded content) | Payload globals + collections; every storefront string reads from Payload (CMS-COUPLING law 1) |
| Site-wide global settings store | Payload `SiteSettings` global (already in `.sps/content-model.md`) — built in S1 |
| Media upload security (MIME/extension whitelist, size cap, traversal guard) | ✅ `cms/src/collections/Media.ts` — MIME whitelist + 15 MB cap |
| 1-click backup | Daily SQLite dump to R2 (`.github/workflows/backup-db.yml`) |
| Round-trip DoD | Admin edit → DB → storefront, proven per section (SECTION-DOD §2.5) |
| Multi-language | Bengali-only UI is an owner decision (`.sps/profile.md`); no i18n toggle |
| In-context visual editor | **Not applicable** — Payload ships its own admin; a second editor would violate rule 6 (surgical scope) |
