## The two decisions you made, and what they cost

### 1. Live-blog updates — opt-in refresh button

Entries are baked into the HTML at build time. That is the reliability story:
with JavaScript off, on a 3G phone, or while the CMS is down, the reader gets the
complete timeline as it stood at the last build — the fallback
`docs/reliability.md` §4 requires.

New updates arrive two ways: the CI rebuild that publishes any other change, or
the **নতুন আপডেট দেখুন** button, which fetches **once**, on tap.

Deliberately not an auto-poll: continuous 30-second polling would put reader
traffic on the 2 GB shared host during exactly the result-day spike the
architecture exists to keep off it — and taking the CMS down would also take away
the newsroom's ability to publish. One request per interested reader instead.

The island clones a `<template>` rendered by the same component that renders the
server-side rows, so the markup exists once. Duplicating a class list between
Astro and a JavaScript string is how the copy readers see ends up stale.

### 2. Poll votes — persisted to the CMS, with guards

`POST /api/polls/:id/vote`. Three guards, in order:

1. **Honeypot** — a `company` field no human sees. A filled one returns a
   normal-looking success **without writing**, so a bot gets no signal.
2. **Rate limit** — 20 attempts per IP per minute, in-process. Cloudflare's free
   tier has no configurable rate-limiting rules (`docs/security.md` §5), so this
   is the only application-layer defence.
3. **Duplicate guard** — `HMAC-SHA256(ip + userAgent, PAYLOAD_SECRET)`, unique
   per poll. A repeat vote returns the current tallies with `alreadyVoted: true`
   — the reader is told the truth instead of having their vote silently dropped.

**Privacy, stated on the widget itself:** the guard row holds a poll reference and
a one-way hash, and **not** which option was chosen, no raw IP, no user agent, no
timestamp. The hash is salted with the server secret, so it is not reversible or
brute-forceable from a leaked database, and the same reader hashes differently
anywhere else.

**Known limitation, stated rather than hidden:** the tally update is a
read-modify-write, so two simultaneous votes for the same poll can lose one
increment. Payload cannot express an atomic `vote_count = vote_count + 1`. For a
reader poll this is an acceptable trade; it would not be for anything counting money.

**Retention gap:** guard rows are meaningless once a poll closes and should be
deleted with it. Payload does not cascade, so closing a poll means deleting its
guard rows by hand. Recorded as an open item below.

## ⚠️ The serious bug this section found: the CSP was breaking every script

**Found by asserting the built HTML, not by looking at a page.** The CSP in
`public/_headers` is `script-src 'self'` with no `'unsafe-inline'` — and Astro
**inlines any component `<script>` that is "small enough"** into the HTML.

So every inlined script was blocked by the browser. Not just the new S8 code:

- the theme toggle (S2)
- the mobile menu (S2)
- the text resizer (S2)
- the demo-ad rotation (S3)
- the copy-link button (S4)
- the `/search` Pagefind bootstrap (S6)

All of it silently dead. **Nothing local ever showed the failure** — the CSP is
applied by Cloudflare Pages, and the site has not been deployed yet. This would
have shipped as "the site is broken and we don't know why".

**Three fixes:**

1. **`vite.build.assetsInlineLimit: 0`** in `astro.config.mjs` — forces every
   asset *and component script* to be emitted as an external file. This was the
   big one. Vite's default is 4096 bytes.
2. **`public/theme-init.js`** — the anti-FOUC theme script moved out of
   `Layout.astro`. It must run before paint, and an inline script cannot; a
   same-origin `<script src>` with no `async`/`defer` is still parser-blocking, so
   it keeps the guarantee and satisfies the CSP.
3. **`public/search-init.js`** — the Pagefind bootstrap, same reasoning.

`ArticleAudio` used `define:vars`, which **always** emits an inline script. It now
takes its text from a `type="application/json"` tag, which is not executable and
so is not subject to `script-src`.

**Result: 0 executable inline scripts across all 28 built pages**, verified by
walking every `.html` in `dist/`. The strict profile can now stay strict.

**Side effect worth knowing:** `assetsInlineLimit: 0` also stopped Astro inlining
small stylesheets into the HTML, so the CSS bundle now contains everything. The
poll's reveal rule had been inline in the HTML all along — which is why the first
verification run could not find it in `_css`.

## Article content blocks

Three Payload `BlocksFeature` blocks, renderable inside an article body:
**infographic**, **before/after** and **scrollytelling**.

None of them depends on JavaScript for its meaning:

- infographic → a `<figure>` with a caption and source
- before/after → **both images stacked**, in legend order, with a real
  `<input type="range">` that only appears once the script can drive it
- scrollytelling → an ordered `<ol>` of steps

The scripts only add a comparison slider and a scroll animation. `richtext.ts`
renders each `blockType` explicitly and falls through to children for anything
unrecognised, so an unknown block can never swallow an article's text.

**Images reserve their box.** Real `width`/`height` are emitted when Payload
recorded them; when they are missing the image gets a 16:9 box with
`object-fit: contain`. A reserved box of the wrong ratio letterboxes the image —
a cosmetic cost. An unreserved box is a layout shift — a budget failure.

## Quiz — the zero-backend trade-off, stated

Grading happens in the browser, so **the correct answers are in the page**. A
determined reader can find them. That is inherent to a quiz with no server, and it
is fine here because this is **practice, not assessment** — nothing is scored for
a certificate and nothing is stored about the reader. A quiz that claimed to be an
exam would need a backend; this one deliberately does not claim that.

The data travels in a `type="application/json"` tag rather than through
`define:vars`, because `define:vars` emits an inline script the CSP would block.

**Streak is days-in-a-row**, not questions-in-a-row — for a daily quiz, coming back
tomorrow is the behaviour worth rewarding. Rolled over at Asia/Dhaka midnight.

## Notes for review

- **A demo live blog, poll and quiz are seeded** so the features are visible:
  `pnpm --filter @shikkha24/cms seed:demo`. The live blog is
  `/live/demo-hsc-result-live`, the quiz is at `/quiz`, and the poll sits in the
  homepage right rail. All are throwaway, like the rest of the demo content.
- **The poll opens with zero votes on purpose.** Seeding a standing would be
  inventing reader opinion and showing it as fact.
- **`PUBLIC_CMS_ORIGIN` must be set for the two islands to render.** Unset, the
  refresh button and the vote control are simply not rendered — an unconfigured
  deploy degrades to static content rather than showing a control that cannot work.
- **The CSP `connect-src` needs the real CMS hostname.** It currently contains the
  placeholder `https://cms.shikkha24.com`, which must match `PUBLIC_CMS_ORIGIN`
  exactly. Owner-blocked on DNS.
