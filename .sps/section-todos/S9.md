## What was built

### Media pipeline — moved off R2 to the host disk

| File | Role |
|---|---|
| `cms/src/collections/Media.ts` | `upload.formatOptions` converts the **stored** file to WebP; `withMetadata: false` strips EXIF |
| `cms/src/lib/media-quota.ts` | Per-day upload cap, enforced before the write |

The original is **not** retained. The owner's decision (2026-09-12) was that R2's
card-on-file overage risk was worse than the host disk's storage ceiling — and
`docs/backup-and-recovery.md` now has to include `data/media/`, which is recorded
as a deferred item.

### Newsletter — self-built, transport-agnostic

`NewsletterSubscribers`, `NewsletterCampaigns`, `lib/mailer.ts`, `lib/campaign.ts`,
four endpoints plus `status`. The transport is cPanel SMTP behind a **hard hourly
cap in code**, because cPanel truncates silently past its limit rather than
refusing — so a campaign is a **resumable batch**: it records a `sentThroughId`
cursor and picks up where it stopped. Ids are monotonic, so the cursor cannot
skip a subscriber.

### Comments, bookmarks, citizen journalism

`POST /api/comments/submit`, `POST /api/citizen/submit`, `/bookmarks`,
`/citizen`, `BookmarkButton`, `lib/bookmarks.ts`.

The generated REST routes could not do the job for the two write endpoints: they
cannot rate limit, cannot honeypot, and cannot check that the target article
exists. See *The security fact*, below.

### Photo galleries

`/gallery`, `/gallery/[slug]`, `ImageGallery`. Each image links to its own
full-size file rather than opening a scripted lightbox, so **no JavaScript is
needed to view a gallery**. `/gallery` stayed on the **strict** CSP — the relaxed
profile it originally had was justified by an ad slot that does not exist.

### Video embeds — click-to-load

`cms/src/blocks/VideoEmbedBlock.ts`, the renderer in
`frontend/src/lib/content-blocks.ts`, the click handler in
`ContentBlockScripts.astro`.

**Nothing is requested from YouTube until the reader taps play.** In the whole
build: `youtube-nocookie` **0**, `ytimg.com` **0**, `<iframe>` **0**. The embed
URL exists in exactly one hashed bundle and is constructed on click.

The poster is a **self-hosted upload** on purpose. YouTube's own thumbnail URL
would be a third-party request on every article view — the exact thing the block
exists to avoid — so a video with no poster renders a text-only trigger rather
than reaching for one.

The trigger is a real `<a>` to the watch page: with JavaScript off the reader
still reaches the video.

### Push notifications + N7 deadline reminders

`PushSubscriptions`, `lib/push.ts`, `endpoints/push.ts`, `frontend/public/sw.js`,
`lib/push.ts`, `DeadlineReminder.astro`.

VAPID keys are **self-generated** — free, no account, no card. `web-push@3.6.7`
is the project's first non-MIT dependency (**MPL-2.0**, file-level copyleft; fine
unmodified). Hand-rolling VAPID + aes128gcm would have been ~150 lines of
untestable crypto, so the dependency was taken and the licence recorded here per
agent rule 8.

### Social login

`lib/signed-token.ts`, `lib/reader-session.ts`, `lib/oauth.ts`,
`auth/reader-strategy.ts`, `endpoints/oauth.ts`, `SocialLoginButtons.astro`,
`pages/login.astro`.

Readers have **no password at all** — `disableLocalStrategy` is set, which is
load-bearing rather than cosmetic: `create` validates the password as *required*
whenever `disableLocalStrategy` is falsy, so leaving it on would have made the
OAuth callback unable to create a reader.

`Readers.email` is now **optional and non-unique**. Email is an attribute here,
never an identity — the identity is `provider` + `providerId`. Facebook returns
no address for a phone-registered account, and one person may use the same
address with both providers.

## The security fact this section turns on

All three public write handlers create rows with `overrideAccess: true`, because
there is no session to run access control against. **That bypasses the
collection's field-level restrictions** — including `Comments.isApproved` and
`CitizenSubmissions.status`.

So the protection is not the access rule; it is the **key-by-key whitelist** in
each handler. The harness posts a forged `isApproved: true` and a forged
`status: 'published'` and asserts both are ignored. Anyone editing those files
must keep the whitelist, because nothing else is holding the line.

The same flag appears in `auth/reader-strategy.ts` and is **not** a hazard there,
for a reason worth stating: there it resolves *identity* from a token we signed,
rather than writing attacker-influenced data. The distinction is in the file.

## What is not built

**Bookmark → CMS sync when a reader is signed in.** The browser-local half is
complete and works with no account, which is the half that matters for a reader
who never signs in. The sync half is unblocked now that the auth layer exists,
but it needs a **decision before code**, not more code:

A naive union-merge re-adds a bookmark that was deleted on another device — the
reader deletes something and it comes back, which is worse than never syncing.
Correct behaviour needs the server to become authoritative after the first
upload, plus a marker in local storage so a stale local copy cannot resurrect a
deletion. That policy is a product decision about whose device wins, so it is
raised for the owner rather than guessed at.

Also deliberately **not** implemented: **account linking**. Two provider
identities sharing an email stay two readers. Merging them automatically would be
an account-takeover vector when a provider does not verify email.
